# Stage 1 产品信息架构与统一页面框架设计

## 1. 文档状态

- 日期：2026-06-10
- 范围：`RT-S1-001`、`RT-S1-002`、`RT-S1-003`
- 状态：设计与实施计划已确认，待实现
- 前置条件：Stage 0 审计与迁移矩阵已通过
- 不包含：Stage 2 领域模型建设，以及 Stage 3 至 Stage 11 的业务能力重建

## 2. 设计目标

本阶段把现有 Web 从开发工具集合改造成普通用户可理解的产品入口，同时保留现有真实业务能力和历史深链。

本阶段完成后：

1. 主导航固定为：首页、研究中心、规则与回测、作者画像、策略中心、每日交易、系统管理。
2. 用户从首页能判断当前最重要的下一步操作。
3. 主要页面采用统一业务页面框架。
4. 旧路由由一个集中兼容层映射，不再分散维护。
5. 尚未在后续 Stage 建立的能力明确显示为“能力尚未建立”，不得使用 Mock 或静态统计冒充。
6. Job、Workflow、Artifact、Pipeline 等术语不出现在普通用户主导航和首页。

## 3. 已确认的设计方向

### 3.1 视觉方向

采用“编辑型工作台”：

- 温暖纸张色背景。
- 深绿色侧边栏。
- 陶土色主要操作。
- 首页只突出一个主操作。
- 信息按“下一步、状态摘要、次要详情”分层。
- 不采用通用蓝紫色管理后台视觉。

具体颜色、字号和间距在实施时形成 CSS 变量，并满足现有可访问性要求。

### 3.2 页面层级

桌面端使用：

```text
一级导航侧边栏
→ 页面标题与上下文
→ 横向二级导航
→ 业务页面框架
```

移动端使用：

```text
抽屉式一级导航
→ 可横向滚动的二级导航
→ 单列业务内容
```

不增加第二个固定侧边栏，避免规则、回测和系统管理页面横向空间不足。

## 4. 单一路由事实源

### 4.1 现状问题

当前路由信息分别维护在：

- `web/src/app/router.tsx`
- `web/src/app/navigation.ts`
- `web/src/app/route-registry.ts`
- 页面中的硬编码返回路径
- `web/src/lib/error-recovery.ts`

其中导航、路由名称、描述和兼容关系存在重复事实源，当前首页仍以 `/dashboard` 为正式入口，多个页面仍硬编码返回 `/dashboard`。

### 4.2 目标结构

建立一个集中路由配置，至少描述：

- 路由标识。
- 正式路径。
- 页面名称。
- 页面用途。
- 一级导航归属。
- 二级导航归属。
- 最低权限。
- 页面组件。
- 是否在普通导航显示。
- 兼容路径。
- 兼容提示。
- 退役 Stage 和退役条件。

路由注册、Sidebar、横向二级导航、Topbar 元数据和兼容重定向都从该配置派生。不得再新增独立的正式导航数组或 Route Registry。

现有测试可按职责拆分，但必须验证同一个配置，而不是复制期望列表形成第二套事实源。

## 7. 统一页面体验

### 7.1 页面框架

建立统一业务页面框架，支持以下可选区域：

1. 页面用途。
2. 当前业务步骤。
3. 前置条件。
4. 输入区域。
5. 处理进度。
6. 输出结果。
7. 下一步主要操作。
8. 失败原因和修复动作。
9. 简短使用说明。

每个主要页面必须明确显示：

- 页面用途。
- 输入：没有用户输入时明确写“本页无需输入”，并说明数据来源。
- 处理状态：包括读取中、处理中、部分可用或当前未执行。
- 输出：没有结果时明确说明尚未产生结果及产生条件。
- 下一步主要操作。

当前步骤、前置条件、失败修复和使用说明按业务需要显示。页面不得用空卡片代替说明，也不得隐藏“无输入”“无结果”状态。

### 7.2 状态模型

统一支持：

- `loading`：说明正在读取什么。
- `empty`：说明为什么为空以及如何产生第一条数据。
- `error`：说明发生了什么、影响了什么、如何处理。
- `partial`：列出可用内容、缺失内容和影响。
- `permission_denied`：说明当前角色不可执行，并隐藏高风险操作。
- `unavailable`：说明能力尚未建立或依赖暂不可用。

用户界面不直接显示 HTTP 状态码、异常栈、内部 Job 类型或文件路径。

所有实际渲染页面都必须能表达上述六类状态，包括：

- 七个一级入口及正式二级入口。
- 历史兼容页面。
- 参数化详情和运行详情页面。
- 系统管理页面。
- 中文 404 页面。

纯重定向路由不构成页面，不要求渲染状态。允许复用统一状态组件，但每个渲染页面必须提供符合自身业务的标题、影响、修复动作和下一步，不得只证明组件本身支持这些状态。

### 7.3 旧页面嵌入规则

Stage 1 不重写后续 Stage 才能正式化的业务内部逻辑。旧页面嵌入时：

- 保留真实 API 和真实数据。
- 正式入口通过业务适配层复用旧页面的数据查询、结果展示和安全业务动作，不直接复用工程表单。
- 统一外层页面标题、用途、输入、处理状态、输出、下一步和错误表达。
- 去除主入口中的开发术语。
- 允许管理员在系统管理或运行详情中展开技术信息。
- 不把旧 Schema 标记成新的正式 Schema。

## 8. 首页设计

### 8.1 信息层级

首页严格分为三层：

1. 主操作：只显示一个当前最值得执行的动作。
2. 状态摘要：紧凑展示 TaskList 要求的业务状态。
3. 次要详情：待办和完整流程，可折叠或进入详情页。

首页不再显示最近 Job、最近 Artifact、Worker、目录路径或技术报表。

### 8.2 首页状态

首页回答：

- 今天数据是否就绪。
- 今日盘前是否完成。
- 最近一个交易日盘后是否完成。
- 是否有规则待审核。
- 是否有画像建议待处理。
- 是否有策略建议待处理。
- 当前策略版本。
- 当前市场状态。
- 是否有失败运行。

非交易日按中国交易日历展示最近交易日状态，不使用自然日直接推断“昨日”。

### 8.3 主操作选择

首页主操作由确定性规则选择，不交给 LLM：

1. 数据缺失或异常时，优先“补齐缺失数据”。
2. 交易日盘前未完成时，优先“生成盘前计划”。
3. 最近交易日盘后未完成时，优先“开始盘后复盘”。
4. 有规则待审核时，优先“审核候选规则”。
5. 有可处理建议时，优先“查看优化建议”。
6. 无待处理事项时，显示“查看今日状态”。

若高优先级动作因权限或依赖不可执行，首页必须显示原因，并给出用户实际可执行的替代动作。

### 8.4 尚未建立的能力

Stage 1 不存在正式作者画像建议、策略建议或正式策略版本时：

- 显示“能力尚未建立”。
- 说明将在 Stage 7、Stage 8 或 Stage 10 接入。
- 不显示虚构数量。
- 不把该状态计入用户待办。
- 不创建临时数据库表或静态接口填充首页。

## 9. 首页数据契约

### 9.1 API 选择

复用并扩展现有：

```text
GET /api/ui/v1/system/dashboard
```

不新建第二套首页 API。现有运维字段继续供系统管理使用，新增业务首页字段供首页消费。

### 9.2 响应结构

```text
status
generated_at
profile_id
profile_snapshot_id
health
worker
failed_jobs
duration_summary
freshness
alerts
traces
report
business_date
is_trading_day
latest_trading_day
next_action
business_status
```

其中：

- `business_status` 表示数据、盘前、盘后、规则、画像建议、策略建议、策略版本和市场状态。
- 现有 `health`、`worker`、`failed_jobs`、`duration_summary`、`freshness`、`alerts`、`traces` 和 `report` 保持原字段和语义，继续供系统管理使用。
- 新字段采用向后兼容的增量扩展，不把已有运维字段移动到新的嵌套对象。
- 每个状态必须包含状态值、事实来源、更新时间、目标路径以及不可用原因。
- 单项查询失败时返回 `partial`，不得把缺失值默认为完成、未完成、零或 false。

### 9.3 数据来源原则

实施前必须对每项状态再次通过代码确认真实查询来源。允许使用现有表、Repository 和 Service 聚合，不允许根据文件是否存在或前端路径推断正式业务状态。

如果当前代码没有可靠事实源：

- 返回 `unavailable`。
- 记录原因。
- 指向正确的后续建设 Stage。
- 不创建第二套临时事实源。

## 10. 权限设计

- 七个一级入口均可在导航中呈现，但内容和动作按现有权限控制。
- 非管理员进入系统管理时，默认显示只读系统状态。
- 用户管理、数据库迁移、恢复等高风险操作仅管理员可见。
- 权限不足时不只禁用按钮；页面需说明所需权限和可联系对象。
- 历史深链的权限校验不得因兼容重定向而绕过。

## 11. 响应式设计

### 11.1 桌面端

- 深绿色固定侧边栏，可折叠。
- 页面内容保持可读最大宽度。
- 二级导航位于页面标题下方。
- 首页状态卡采用紧凑网格，主操作占据最高视觉权重。

### 11.2 移动端

- 一级导航使用抽屉。
- 二级导航横向滚动，并清晰标记当前项。
- 首页顺序固定为：主操作、关键状态、待办、流程说明。
- 表格转为可横向滚动或业务卡片，不截断主要操作。
- 不依赖 hover 才能发现入口或说明。

## 12. 错误与兼容说明

所有主要错误状态必须包含：

```text
发生了什么
影响了什么
应该怎么处理
```

旧入口兼容页或兼容提示必须包含：

- 旧入口名称。
- 新正式入口。
- 当前仍保留旧入口的原因。
- 预计退役 Stage 或退役条件。
- 返回新入口的明确按钮。

兼容说明不能阻止用户继续使用仍然有效的真实能力。

## 13. 测试设计

### 13.1 前端单元与组件测试

- 集中路由配置生成七个一级导航。
- 主导航不出现 Job、Workflow、Artifact、Pipeline 等术语。
- 二级导航归属、激活状态和权限过滤正确。
- 统一页面框架覆盖六类状态。
- 首页主操作优先级正确。
- 首页对 unavailable 和 partial 不做错误默认。
- 兼容提示包含目标入口和退役条件。
- 所有实际渲染页面逐页验证用途、输入、处理状态、输出和下一步。
- 页面状态覆盖矩阵逐页验证 loading、empty、error、partial、permission denied 和 unavailable；对业务上不可能自然出现的状态，通过页面适配器注入状态进行测试。
- 正式入口不得渲染内部 Job 类型、Workflow ID、Pipeline Step、Artifact 路径、Provider 名称或 `force` 参数。
- 所有普通用户动作使用中文业务动词；日期、时间和状态说明使用 `zh-CN` 与 `Asia/Shanghai`。

### 13.2 路由测试

- `/` 直接进入首页。
- `/dashboard` 重定向到 `/`。
- `/articles` 进入研究中心。
- `/strategies` 不再重定向首页。
- 全部现有 49 条路由记录均有保留、重定向或兼容处理。
- 每条旧入口逐项具备目标入口、兼容模式、退役 Stage 和退役条件；长期保留项明确标记无需退役。
- 未知路径展示中文 404。
- 页面和错误恢复中的 `/dashboard` 硬编码全部清理或兼容。
- 用户主旅程可沿正式入口完成“研究中心 → 规则审核 → 回测 → 作者画像 → 策略中心 → 每日交易”，不经过 Job、Workflow、Pipeline 或 Artifact 页面。

### 13.3 API 与服务测试

- Dashboard 响应兼容已有字段。
- 每个新增业务状态由真实 Service 或 Repository 提供。

- 缺失事实源返回 unavailable，不返回零值或 false。
- 非交易日使用最近交易日。

### 13.4 回归与人工验收

- 运行受影响的前端测试、类型检查和构建。
- 运行 Dashboard API、SystemService 和相关 Repository 测试。

- 人工确认新用户无需理解内部开发步骤即可找到下一步。

## 14. 实施边界

Stage 1 允许：

- 重构路由、导航、布局、首页和通用状态组件。
- 扩展现有 Dashboard Service 和响应类型。
- 调整旧页面外层体验及兼容提示。
- 修正因正式入口变化产生的内部链接和错误恢复路径。

Stage 1 不允许：

- 新建第二套规则、画像、策略或回测 Schema。
- 提前实现 Stage 2 至 Stage 10 的正式领域模型。
- 用静态数量、Mock 页面、空接口或硬编码流程冒充能力。
- 删除尚未满足迁移矩阵退役条件的历史入口。
- 把现有运维 Dashboard 删除；它应迁入系统管理继续使用。

## 15. 验收门禁
