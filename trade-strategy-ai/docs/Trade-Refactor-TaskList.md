# Trade Strategy AI 面向用户重构 TaskList

## 0. 文档定位

本文档是 `trade-strategy-ai` 本轮重构的主执行清单。

目标不是继续修补现有 Web，而是把项目重构为一个真正面向中国用户的交易研究与每日决策产品。

最终用户流程必须清晰表达为：

```text
文章导入
→ LLM 提取规则
→ 人工审核
→ 历史回测
→ 分市场状态验证
→ 作者方法画像
→ 策略发布
→ 每日盘前
→ 每日盘后
→ 规则、画像和策略持续优化
```

本次重构允许 AI 修改：

- UI 布局和视觉风格。
- 前端路由、页面、组件和状态管理。
- 后端 API、Service、Job、Workflow 和 Pipeline。
- 数据库结构、表、字段、索引和迁移。
- Prompt、Schema、领域模型和运行契约。
- 历史兼容层和旧页面。
- 数据抓取、调度、回测和盘前盘后流程。

只要修改有利于重构目标，可以调整现有实现；但必须保留数据可迁移性、结果可追溯性和完整回归能力。

# 1. 最终产品原则

## 1.1 面向用户，而不是面向开发

最终 Web 中不得把以下技术概念作为普通用户主入口或主要操作语言：

- Job
- Workflow
- Pipeline
- Artifact
- Provider
- Schema
- Snapshot 文件路径
- `kaipan-fetch`
- `kaipan-normalize`
- `ohlcv-crawl`
- `market-state-build`
- CLI 命令
- 内部函数名
- 数据库表名

这些能力可以保留在系统内部或管理员的“运行详情”中，但普通用户看到的必须是业务语言。

例如：

```text
错误：运行 ohlcv-crawl Job
正确：更新历史行情数据

错误：执行 kaipan-normalize
正确：整理盘前市场数据

错误：查看 Artifact
正确：查看本次结果
```

## 1.2 流程必须可理解

每个业务页面必须明确显示：

```text
本页面用于做什么
需要哪些输入
系统会执行什么
会得到什么结果
下一步应该做什么
```

必要时可以在页面顶部或首次进入时加入简短使用说明，但说明必须简洁，不能变成开发文档。

## 1.3 主导航必须收口

最终主导航建议固定为：

```text
首页
研究中心
规则与回测
作者画像
策略中心
每日交易
系统管理
```

说明：

- “作者画像”可以单独作为一级入口，也可以作为“研究中心”或“策略中心”的重要子模块。
- 最终选择应以用户测试和流程清晰度为准。
- Jobs、Workflows、Artifacts 不得继续作为普通用户主导航。

## 1.4 统一使用中文“市场状态”

面向用户统一使用：

```text
市场状态
分市场状态回测
基于市场状态的规则选择
市场状态模型版本
```

代码内部暂时保留 `regime` 字段时，必须有明确兼容映射，不能把英文技术词直接展示给用户。

# 2. AI 执行约束

## 2.1 执行方式

1. 默认每次只处理同一 Stage 中一个明确 Task。只有用户明确指定时，才可处理同一 Stage 中紧密关联、共享已冻结契约且可共同验收的少量 Task；不得跨 Stage 合并执行。
2. 实现前必须阅读本 TaskList、重构方案和 Prompt 说明。
3. 不得脱离本 TaskList 自行新增业务方向。
4. 可以大范围修改代码，但必须说明迁移方式和回归影响。
5. 不得只完成后端或只完成前端就宣称业务闭环完成。
6. 每个 Stage 必须包含可见、可操作、可验证的用户结果。
7. 每次修改必须更新测试、迁移说明和用户文档。
8. 发现现有实现与目标冲突时，优先保证目标产品正确，而不是保留旧页面结构。
9. 不允许为了兼容而长期保留两套正式入口、两套正式 Schema 或两套策略事实源。
10. 旧能力可以保留为过渡层，但必须标注退役条件。

## 2.2 允许修改范围

本次重构允许：

- UI 布局和视觉风格。
- 重写主路由和 Sidebar。
- 合并或删除旧页面。
- 重建数据库模型。
- 调整 API 契约。
- 重构 Job/Workflow 组织方式。
- 引入新的领域对象和版本对象。
- 迁移旧数据。
- 重构 Prompt 调用链。
- 调整调度逻辑。
- 替换不合适的前端布局和交互。

## 2.3 禁止事项

- 不得把旧页面简单换皮后称为完成。
- 不得继续以“工具入口列表”作为产品首页。
- 不得要求普通用户手动理解前置任务链。
- 不得让用户自己在多个页面拼接完整流程。
- 不得让 LLM 推断结果直接覆盖正式规则、画像或策略。
- 不得让回测依赖实时数据源。
- 不得把缺失数据默认为 false、0 或“已满足”。
- 不得出现无法追溯的数据、规则、画像或策略版本。
- 不得让单日盘后结果直接修改正式策略或正式画像。

---

# 2.4 阶段出口条件

每个 Stage 只有同时满足以下条件，才允许进入下一阶段：

1. 本阶段定义的用户流程可以使用真实数据走通。
2. 前端、后端、数据库和运行契约一致。
3. 所有验收标准逐条满足。
4. 受影响测试实际运行并通过。
5. 数据迁移或兼容方案已验证。
6. 实施记录已更新。
7. 没有未说明的阻塞项。
8. 没有新增第二套正式入口或事实源。

每个 Stage 必须提供至少一条面向用户的演示路径，而不是只提交代码文件。

# 4. Stage 0：现状审计与重构边界

## 目标

在修改业务实现前，完整识别现有前端、后端、数据库、Prompt、数据流和兼容入口，避免重复实现或误删。

## 任务

### RT-S0-001 现状审计

检查并记录：

- 当前主导航、Sidebar、路由和页面。
- 当前文章、规则、回测、画像、策略、盘前、盘后入口。
- 当前 Job、Workflow、Pipeline 和调度能力。
- 当前数据库模型和主要表。
- 当前 Prompt 文件和调用方式。
- 当前 OHLCV、Kaipan 和市场状态数据链路。
- 当前策略版本和规则适用性实现。
- 当前 legacy 入口和兼容逻辑。

### RT-S0-002 迁移矩阵

输出：

```text
现有能力
→ 保留
→ 改造
→ 合并
→ 迁移
→ 退役
```

每个旧入口必须明确：

- 新入口。
- 数据迁移方式。
- 允许保留到哪个 Stage。
- 最终是否删除。

## 验收

- 不修改核心业务行为。
- 形成可执行迁移矩阵。
- 找出所有重复入口和事实源。
- 明确哪些代码可以复用，哪些必须重构。

## 任务

接入并统一以下 Prompt：

```text
prompts/article_analysis_v1.md
prompts/article_analysis_repair_v1.md
prompts/concept_extraction_v1.md

prompts/llm_attribution_v1.md

```

Prompt 契约说明：

```text
docs/PROMPT_REVIEW_AND_MIGRATION.md
docs/AUTHOR_PROFILE_PROMPT_FLOW.md
docs/LLM-Prompt-Orchestration.md
```

调用编排必须遵循：

```text
单篇普通文章：
article_analysis_v1
→ 通常 1 次主调用

校验失败或局部缺失：
article_analysis_repair_v1
→ 按需 0～1 次

作者画像：
按 10～20 篇或事件批次调用

盘后归因：

```


要求：

- Prompt 和 Schema 必须版本化。
- 输出必须通过 Pydantic 或 JSON Schema 校验。
- 文章未声明市场状态时必须为 `not_declared`。
- LLM 推断与文章事实分离。
- LLM 不得自行计算回测指标。
- 每条重要结论保留证据。
- 旧 Prompt 可短期保留用于对照测试，但不能长期形成第二套正式链路。

### RT-S3-002 单篇文章到候选规则闭环

实现：

```text
导入文章
→ 清洗
→ 单篇结构化
→ 候选规则提取
→ 明确前置条件提取
→ 用户审核
→ 形成正式规则版本
```

页面必须显示：

- 原文。
- 摘要。
- 方法标签。
- 候选规则。
- 证据。
- 缺失信息。
- 可回测状态。
- 是否依赖 Kaipan。
- 市场状态是否明确声明。

版本来源要求：

- 摘要和其他绑定历史版本的字段必须追溯到当前选中的
  `ArticleRevision` 或对应内容版本。
- 优先使用 `ArticleRevision` 自身冻结的摘要来源。
- 仅当当前文章记录的内容 hash 与所选 `ArticleRevision` 的内容 hash
  一致时，才允许使用当前文章摘要。
- 无法证明版本对齐时，API 和 UI 必须显示摘要不可用，不得回退到最新
  文章摘要，也不得猜测或无证据回填。
- 摘要来源与 `ArticleStructure` 的 Prompt/Schema/版本来源必须分别记录、
  展示和验证。
- 历史摘要不可用是合法的数据质量状态，不阻塞规则提取、审核、回测及
  后续流程，但后续页面和服务必须继续尊重该状态。

### RT-S3-003 建立回归样本并批量处理现有 100+ 篇文章

黄金样本集不是用户开始重构前必须提供的输入。

Stage 3 开始时，由系统从现有文章中自动筛选候选回归样本，AI 按类别整理，用户只需快速确认。

候选样本至少覆盖：

- 规则明确。
- 纯概念。
- 混合内容。
- 具体复盘案例。
- 含市场状态描述。
- 未声明市场状态。
- 含模糊词。
- 依赖 Kaipan。
- 重复规则。
- 冲突观点。

初始可先建立 10～15 篇临时回归样本，并固定：

- article_id。
- 输入内容版本。
- Prompt 版本。
- 当前输出。
- 自动审核结果。
- 人工确认结论。

在固定回归样本通过前，不得批量重跑全部文章。

批量处理采用：

```text
逐篇结构化
→ 去重聚类
→ 每 10～20 篇批次画像
→ 规则指纹
→ 规则族
→ 作者总画像草稿
```

要求：

- 不把所有全文一次性发送给 LLM。
- 支持断点续跑。
- 支持失败重试。
- 支持增量更新。
- 输出文章、规则和画像质量统计。
- Prompt 或审核规则变更后，先运行固定回归样本。

### RT-S3-004 旧 Prompt 迁移与退役

旧 Prompt 包括但不限于：

```text
concept_extraction.md
rule_extraction.md
precondition_extraction.md
llm_attribution.md
llm_postmortem_notes.md
```

退役流程：

```text
active
→ deprecated
→ compatibility_only
→ unused
→ deleted
```

要求：

- 新旧 Prompt 先使用固定回归样本对照。
- 新 Prompt 成为唯一正式生产入口后，旧 Prompt 只能用于兼容读取。
- 旧 Prompt 不得继续产生新的正式数据。
- 完成新旧 Schema 映射。
- 历史结果必须继续可读。
- 删除前必须完成代码、测试、脚本、Job、Workflow 和文档无引用检查。
- 删除前必须完成观察期和回滚验证。
- 删除后只通过 Git 历史保留旧内容，不需要长期维护 legacy Prompt 目录。

## 验收

- 固定代表性文章集测试通过。
- 用户可以完成“文章到正式规则”。
- 100+ 篇文章可批量、增量和可恢复处理。
- Prompt 结果可追溯到版本和原文证据。
- 普通文章默认只进行一次统一主调用，失败时最多一次定向修复。
- 作者画像 Prompt 不得逐篇调用。
- 盘后归因 Prompt 仅按条件触发。
- 新 Prompt 已成为唯一正式调用链。
- 旧 Prompt 满足删除验收后已彻底删除；若未满足，必须保持 deprecated 状态且不得标记 Stage 3 完成。
- 所选历史文章版本的摘要不得泄漏或回退到最新文章摘要。
- 无法证明 revision 对齐的摘要必须保持 unavailable；回归 fixture
- 不得伪造“可用摘要”。

# 8. Stage 4：规则管理、去重和规则族

## 目标

让规则从 LLM 输出变成可审核、可回测、可版本化的正式资产。

## 任务

### RT-S4-001 自动审核与人工审核工作台

建立“两级审核”机制：

```text
LLM 提取候选规则
→ 自动审核与风险分级
→ 低风险规则进入待回测
→ 有歧义或高风险规则进入人工审核
→ 回测验证
→ 正式启用前人工确认
```

自动审核至少检查：

- Prompt 和 Schema 是否合法。
- 是否包含原文证据。
- 条件和动作是否完整。
- 是否存在模糊词和未定义参数。
- 是否缺少退出、失效或持有周期信息。
- 市场状态是否来自文章明确声明。
- 是否依赖当前不可获得的数据。
- 是否与已有规则重复或冲突。
- 是否具备回测条件。
- LLM 置信度和规则影响等级。

自动审核结果统一为：

```text
自动通过
建议通过
需要人工确认
不可回测
建议拒绝
```

“自动通过”只表示可以进入待回测，不表示已经成为正式可用规则。

人工审核工作台必须支持：

- 查看规则来源和原文证据。
- 查看自动审核结果、原因和风险等级。
- 修改条件和参数。
- 标记模糊词和缺失字段。
- 查看数据依赖和可回测状态。
- 查看重复规则和冲突规则。
- 批准、修改后批准、合并、暂存或拒绝。
- 批量批准低风险规则。
- 批量拒绝明确无效规则。
- 仅筛选“需要人工确认”的规则。

以下情况必须人工审核：

- 需要补充或修改参数。
- 涉及仓位、止损、止盈或风险控制。
- 市场状态由 LLM 推断。
- 依赖 Kaipan 或复杂市场上下文。
- 与已有规则重复或冲突。
- 多篇文章表达不一致。
- 准备进入正式策略。

所有人工操作必须记录审核人、时间、修改前后内容和审核原因。

### RT-S4-002 规则指纹与规则族

实现：

- 高度相似规则检测。
- 重复规则合并。
- 参数变体管理。
- 规则冲突检测。
- RuleFamily。
- 来源文章关联。

### RT-S4-003 规则生命周期

统一：

```text
候选
→ 待审核
→ 已批准
→ 待回测
→ 验证中
→ 可用
→ 限定使用
→ 已停用
```

## 验收

- 自动审核能够筛出低风险、需人工确认、不可回测和建议拒绝规则。
- 低风险规则可以批量进入待回测，但不能自动成为正式可用规则。
- 高风险、歧义、冲突和策略入选规则必须经过人工确认。
- 人工审核 UI 能展示证据、自动审核原因、缺失项、数据依赖和冲突信息。
- 所有审核动作有完整审计记录。
- 不再对大量重复规则重复回测。
- 用户能理解规则当前状态。
- 每条规则都有来源、版本、证据和数据依赖。
- 市场状态未声明不阻止规则进入探索性回测。

# 17. 每个任务的完成标准

任何任务只有同时满足以下条件才能标记完成：

7. 数据迁移或兼容方案完成。

9. 页面是否完全避免不必要的开发术语？
