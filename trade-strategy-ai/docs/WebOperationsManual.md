# Web 运维管理手册

> 适用范围：`trade-strategy-ai` 的 Web 管理后台运维、部署、监控、备份与恢复责任人。
>
> 目标：给出可执行的运维顺序，明确高风险操作边界、回滚路径和排障入口，避免把配置恢复、项目恢复和页面浏览混在一起。

---

## 1. 你会用到什么

- 后端入口：`api/main.py`
- Web 前端：`web/`
- 配置恢复：`Settings`
- 项目级备份/恢复：`Ops`
- 健康检查：`/health`、`/api/ui/v1/system/status`
- 运维摘要：`/data-health`
- 主手册：[`docs/WebUserManual.md`](WebUserManual.md)
- 部署说明：[`docs/WebDeployment.md`](WebDeployment.md)

如果你是第一次接手运维，建议先按这个顺序熟悉：

1. 看 `WebDeployment.md`，确认运行拓扑和启动顺序。
2. 看 `WebUserManual.md`，确认页面入口和高风险操作位置。
3. 再看本手册，确认恢复、回滚和排障流程。

---

## 2. 运维前提

### 2.1 必要环境

- PostgreSQL 已启动并可连接
- `DATABASE_URL` 已配置
- `config/app.yaml` 已存在
- `X-API-Key` 已在浏览器或调用端注入

### 2.2 常用目录

- `config/`：应用配置
- `data/backups/`：配置备份和项目快照
- `data/artifacts/`：任务产物
- `data/processed/`：项目级恢复会用到的处理后数据
- `logs/`：API 和 Worker 日志

---

## 3. 启动与健康检查

### 3.1 推荐启动顺序

1. 启动 PostgreSQL
2. 执行数据库迁移
3. 启动 API
4. 启动 Worker
5. 启动或托管 Web 前端
6. 检查 `Overview`、`Data Health`、`Jobs`

### 3.2 先看什么

建议先看这三个位置：

- `/health`：服务是否活着
- `/api/ui/v1/system/status`：API、数据库、目录状态
- `/data-health`：运维摘要、失败任务、告警和追踪线索

如果这三处有错误，不要先处理业务页面。

---

## 4. 配置恢复

配置恢复只由 `Settings` 页面负责，目标是 `config/app.yaml` 及其受管配置。

### 4.1 适用场景

- 配置改错
- API key 或 Cookie 误写
- 数据库连接串切换
- 某个配置段需要回滚

### 4.2 操作原则

- 只允许 `admin`
- 恢复前必须确认
- 恢复结果要保留审计
- 页面只展示脱敏值

### 4.3 排障提示

如果配置恢复失败，优先检查：

- 备份路径是否位于 `data/backups/`
- 配置路径是否位于项目根目录内
- 保存/恢复是否被编辑锁占用
- 配置文件是否能被当前进程读写

---

## 5. 项目级备份与恢复

项目级备份与恢复只由 `Ops` 页面负责，不要和 `Settings` 混用。

### 5.1 备份内容

项目级快照会包含：

- 数据库表数据
- Job 元数据
- 审计记录
- `data/processed`，如果启用 `include_processed`

### 5.2 创建备份

在 `Ops` 页面点击 `Create backup`。

建议操作前先确认：

- 当前环境是不是正确环境
- 是否需要包含 `data/processed`
- 备份目录是否仍有足够磁盘空间

### 5.3 恢复备份

恢复前必须：

- 选择快照
- 二次确认
- 以 `admin` 身份执行

恢复后建议立即检查：

- `Jobs` 是否能继续领取任务
- `Data Health` 是否恢复正常
- 相关产物是否能被重新索引

### 5.4 回滚演练

推荐的生产回滚步骤：

1. 先创建当前状态的项目快照。
2. 在测试环境恢复一份已知快照。
3. 验证恢复后的系统状态、任务状态和产物路径。
4. 发布失败时，恢复上一份已验证快照。
5. 如果问题只出在配置，再回到 `Settings` 恢复配置备份。

## 6. 监控与告警

### 6.1 关注哪些页面

- `Data Health`
- `Jobs`
- `Overview`
- `Reports`

### 6.2 关注哪些信号

- 最近失败任务
- 任务耗时异常
- 数据新鲜度异常
- 告警摘要
- 日志追踪线索

### 6.3 追踪顺序

1. 先看 `Data Health`。
2. 再看对应的 `Job`。
3. 再看该 Job 的日志和产物。
4. 最后看系统状态和配置。

---

## 7. 常见故障

### 7.1 页面打不开

先确认：

- API 是否启动
- `X-API-Key` 是否正确
- 前端静态资源是否已构建

### 7.2 任务一直失败

先确认：

- Job 参数是否正确
- 数据库是否可写
- 产物目录是否可写
- 相关配置是否脱敏后仍保持有效值

### 7.3 恢复后数据不对

先确认：

- 是否恢复了正确的快照目录
- `manifest.json` 是否存在
- `processed/` 是否真的被包含
- 恢复前是否有新的写入覆盖了结果

---

## 8. 责任边界

- `Settings` 管配置文件
- `Ops` 管项目快照和回滚演练
- `Data Health` 管运维摘要和告警
- `Jobs` 管长任务执行和日志

如果你在一个页面里发现了不属于它的高风险动作，先停下来，不要继续把它当成正常页面操作。
