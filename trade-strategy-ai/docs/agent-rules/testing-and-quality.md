# Testing and Quality Rules

## 1. 代码规范

- 类、方法、配置项必须有中文注释解释作用
- 不允许遗留无意义 debug `print`
- 不允许硬编码敏感信息
- 不允许把环境相关路径写死
- 不允许在核心逻辑中混入临时测试代码
- 修改公共方法时必须检查调用方
- 修改配置项时必须检查默认值和兼容性
- 代码结构应保持可读、可维护、可测试

---

## 2. 编写即测试

完成独立函数或模块后，应：

- 编写单元测试
- 或在现有测试文件中补充测试

测试文件通常位于：

```text
tests/
```

并尽量与源文件结构对应。

---

## 3. 修改即验证

修改现有代码后，必须运行相关测试，防止回归。

验证范围应与修改范围匹配：

| 修改类型 | 推荐验证 |
|---|---|
| 单个函数 | 单元测试 |
| API | API 测试 / contract 测试 |
| UI | UI 状态和交互验证 |
| workflow | 集成测试 |
| schema | migration / fixture 验证 |
| config/profile | 默认值和兼容性测试 |

---

## 4. 提交即整洁

完成一组开发任务后，必须确认：

- lint 通过
- 测试通过
- 没有无用调试代码
- 没有临时文件
- 没有敏感信息泄露
- 没有未记录的行为变化

---

## 5. 无法运行测试时

如果无法运行测试，必须明确说明：

```md
## 未运行测试

原因：
风险：
建议补充验证：
```

禁止：

- 未运行测试却写“测试通过”
- 忽略测试失败继续宣称完成
- 把 REVIEW 任务标记 DONE

---

## 6. 错误处理与恢复

当命令、修改、测试或构建失败时：

1. 阅读错误日志
2. 定位失败原因
3. 尝试最小修复
4. 再次验证
5. 如果仍失败，换一个策略
6. 建议最多尝试 3 次
7. 仍失败时停止操作并汇总

汇总格式：

```md
## 问题

## 错误信息

## 已尝试方案

## 结果

## 当前判断

## 建议下一步

## 是否需要用户确认
```

禁止：

- 忽略错误继续推进
- 未验证就宣称已修复
- 用大规模重构掩盖小问题
- 为修复一个错误引入多个未确认变化
