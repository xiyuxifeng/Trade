# Goal-Driven Rebuild TaskList

> 本 TaskList 只服务一个目标：把项目重构成用户打开 Web 后就能清楚知道怎么用、每一步做什么、最后得到什么结果的产品。
>
> 允许为达成最终用户目标而调整、删除、合并 Web 页面、数据库结构和现有代码逻辑。
>
> 但任何改动都必须围绕主链路：
>
> ```text
> 博客文章 -> 规则提取 -> 回测验证 -> 交易员画像 -> 盘前预测 -> 盘后复盘
> ```
>
> 不允许新增新的对外主概念来替代这条主链路。

---

## 0. 执行原则

1. 先保证用户目标，不为现有实现形式让路。
2. 任务不拆到过细，但每个任务必须能看出业务目标。
3. 所有页面、数据、Job、文案、接口都必须围绕统一主线。
4. 允许重构时修改或删除旧页面、旧表、旧逻辑，只要最终用户目标更清晰。
5. 不能把内部实现名词继续作为用户主入口。
6. 不能保留会持续制造漂移的双轨概念。

## 1. 推荐执行顺序

为了保证每一步都能推进到最终用户目标，建议按下面顺序执行：

1. `GD-R1` 先收口用户目标、主入口和入口分层。
2. `GD-R2` 再收口市场数据链路，统一市场上下文快照。
3. `GD-R3` 之后重构 Job 中心，让提交、状态、详情、操作都清晰。
4. `GD-R4` 再重构主业务页面和文案，让用户可以完整走通主流程。
5. `GD-R5` 最后清理旧入口、兼容层和冗余实现，并做最终验收。

### 执行依赖

- `GD-R1` 是所有任务的前置条件。
- `GD-R2` 需要 `GD-R1` 先完成主线与概念收口。
- `GD-R3` 需要 `GD-R1` 先完成入口分层，避免 Job 再次被放错位置。
- `GD-R4` 依赖 `GD-R1`、`GD-R2`、`GD-R3` 的结果，才能把页面和交互一次性收口。
- `GD-R5` 必须最后执行，作为退役旧入口和最终验收的收尾任务。

## 2. 入口处理策略

当前 Web 端入口必须按下面三类处理：

### 2.1 保留

这些入口应保留为正式入口，只是需要按新的产品叙事重新命名或降级展示：

- `/jobs`
- `/jobs/:jobId`
- `/articles`
- `/backtest`
- `/market`
- `/profiles`
- `/system`
- `/artifacts`

### 2.2 替换

这些入口保留路径或能力，但对外表达、位置、导航级别需要替换：

- `/dashboard`
- `/market/snapshots`
- `/market/datasets`
- `/rule-pool`
- `/articles/run`
- `/market/kaipan`
- `/market/ohlcv`

### 2.3 废弃为主入口

这些入口不再作为主导航出现，必要时仅保留兼容跳转：

- `/strategies`
- `/workflows/*`
- `/admin/*`
- `/settings`
- `/alerts`

> 说明：
> - “废弃为主入口”不等于立刻删路由。
> - 允许保留兼容层，但不得继续作为正式导航和正式叙事出现。
> - 兼容层在全局壳和状态展示中只能以“兼容访问 / 历史链接”等收口口径出现，不应继续把原始路径当作正式 Route 叙事暴露给最终用户。

## 3. 任务清单

### [x] GD-R1 统一用户主流程和 Web 入口

目标：

- 收口首页和主导航。
- 让用户一进入 Web 就知道从哪里开始。
- 让主流程只围绕文章、规则、回测、画像、盘前、盘后展开。
- 保留 Job List、Dashboard 和配置管理入口，但明确分层，不让它们抢占主流程。

范围：

- 首页导航
- 页面分组
- 页面标题与说明
- 对外入口排序
- Job List
- Dashboard
- 配置与管理入口

依赖：

- 无。该任务是所有后续任务的前提。

验收标准：

- 用户不需要理解内部概念就能找到主流程入口。
- 首页能直接指向文章、回测、盘前、盘后和市场上下文。
- 不再出现多个并列的、互相解释不清的主入口。
- Job List 作为任务中心保留且可直达。
- Dashboard 作为概览页保留但不作为主流程入口。
- 配置与管理入口下沉到次级导航，不与主流程并列。
- 一级入口、子入口的保留 / 替换 / 废弃关系与 [Entry-Subentry-Matrix.md](./Entry-Subentry-Matrix.md) 一致。
- 用户从文章导入到盘后复盘的屏到屏路径必须能闭环，不需要返回首页重新寻找下一步。

---

### [x] GD-R2 收口市场数据链路，建立单一市场上下文快照

目标：

- 统一市场数据流向。
- 让盘前、盘后、回测消费同一套市场上下文。
- 取消重复抓取、重复标准化、重复快照构建。

范围：

- `kaipan-fetch`
- `kaipan-normalize`
- `snapshot-build`
- 市场上下文快照
- 相关数据存储与读取路径

依赖：

- `GD-R1`

验收标准：

- `kaipan-fetch` 不再承担标准化职责。
- `kaipan-normalize` 不再重新抓取。
- `snapshot-build` 不再绕回 raw/provider。
- 对外只保留一套可解释的市场上下文表达。

---

### [x] GD-R3 重构 Job 语义和进度展示

目标：

- 让 Job 只做调度、状态记录和结果记录。
- 让进度条和终态明确分离。
- 避免用户把进度百分比误认为成功状态。
- 让用户可以直接理解 Job 当前状态，并对 Job 进行暂停、恢复、取消等操作。
- 让用户可以看到 Job 的成功、失败、进行中等统计信息。

范围：

- Job 状态展示
- Job 进度展示
- Job 日志和结果页
- 相关后端状态流转
- Job 操作入口
- Job 统计信息

依赖：

- `GD-R1`

验收标准：

- 100% 进度不再等同于成功。
- 失败、取消、处理中、成功四种终态清晰可见。
- Job 不再混合承担业务转换语义。
- Job 详情页可以清晰显示当前状态、进度和统计信息。
- Job 支持暂停、恢复、取消操作，且状态流转可追踪。
- 用户可以清楚看到成功多少、失败多少、进行中多少。
- Job 统计口径必须统一，并在列表页和详情页保持一致。

---

### [x] GD-R4 重构 Web 页面与文案

目标：

- 让 Web 端像一个可直接使用的产品，而不是技术入口集合。
- 页面文案、按钮文案、空状态、错误状态统一表达。
- 降低用户理解和使用成本。

范围：

- 首页
- 文章与规则页
- 回测与画像页
- 盘前分析页
- 盘后复盘页
- 市场上下文页
- Job 详情页

依赖：

- `GD-R1`
- `GD-R2`
- `GD-R3`

验收标准：

- 用户能直接通过页面文案理解每一步做什么。
- 页面不再默认暴露内部实现名词。
- 关键状态都有明确的下一步提示。

---

### [x] GD-R5 清理冗余实现并完成最终验收

目标：

- 清理不再服务主目标的冗余页面、冗余数据路径、冗余概念。
- 验证最终用户链路完整可用。
- 确认重构后的实现不会再次漂移。

范围：

- 冗余 Web 页面
- 冗余数据库或数据路径
- 冗余概念和文档引用
- 最终验收测试与人工检查

依赖：

- `GD-R1`
- `GD-R2`
- `GD-R3`
- `GD-R4`

验收标准：

- 用户从 Web 可以完整走通主链路。
- 所有入口和说明都围绕最终目标。
- 不再保留会持续制造混淆的并行主概念。
- 文档、TaskList、页面入口和数据契约一致。
- `Entry-Subentry-Matrix.md` 中标记为“废弃为主入口”的页面，不再出现在正式导航中。
- `Entry-Subentry-Matrix.md` 中标记为“替换”的页面，必须完成对外表达和职责替换。
- 全局壳对兼容页面只显示收口后的兼容口径，不再把兼容路径作为正式 Route 叙事。
- 主链路闭环必须能从文章一路走到盘后复盘，不依赖重新回到首页再次选择流程。

补充收口：

- `candidates` 的实际能力保留为 `backtest` 体系内的独立子页面 `/backtest/candidates`，由回测页提供轻入口，不再作为独立 `/strategies/candidates` 页面或主导航入口。
- 候选版本生成、候选列表、候选审核动作都应保留在候选子页面中，回测页只保留轻入口和说明，不打断主流程。

## 6. 反漂移约束

下面这些约束是本次重构的硬规则，任何任务都不能突破。

### 4.1 只保留一条对外主线

对外只保留这一条主叙事：

```text
博客文章 -> 规则提取 -> 回测验证 -> 交易员画像 -> 盘前预测 -> 盘后复盘
```

任何新页面、新按钮、新概念、新文档，如果不能映射回这条主线，就不能作为正式入口保留。

### 4.2 旧概念必须退役

允许在实现层保留旧概念作为内部中间层，但不允许长期并列成用户可见的主概念。

例如：

- `MarketUniverse`
- `Market Snapshot`
- `snapshot-build`

这些都必须最终收口到统一的“市场上下文快照”表达，不允许继续作为并列主入口存在。

### 4.3 不允许双轨事实源

任何市场数据、规则数据、Job 数据、页面入口，都必须有唯一事实源。

禁止：

- 一套数据给 Web 用，另一套数据给回测用。
- 一套 Job 状态给列表用，另一套状态给详情页用。
- 一个概念在文档里解释成 A，在页面里解释成 B。

### 4.4 不允许隐性扩张

如果实现过程中发现需要新增能力，必须先判断它是否服务于最终用户目标。

如果不服务于主线，默认不做。

如果服务于主线，但会新增新的对外概念，必须先定义退役旧概念的方式，再允许实现。

### 4.5 允许调整的范围

为了实现最终用户目标，允许在重构中调整、删除或合并：

- Web 页面
- 数据库结构
- 现有代码逻辑
- Job / Workflow 语义
- 文案和入口层级

但所有调整都必须满足：

1. 用户目标更清晰。
2. Web 入口更清晰。
3. 数据流向更单一。
4. Job 语义更明确。
5. 不新增长期漂移风险。
