## 3. 代码缺陷与设计缺陷

### 3.1 严重缺陷（影响功能正确性）

#### D1: `BacktestEngine` 每日仅处理首个 candidate（功能缺失）【已修复】

```python
# src/backtest/engine.py:249
candidates = replay_candidates(strategy_version, market_context)
# ...
candidate = candidates[0]   # 只取第一个！
```

**问题**: 一个 `StrategyVersion` 通常包含多条 `recommendations`（多标的建议），但引擎每天只生成**一条** `BacktestTradeRecord`，其余 candidate 被静默丢弃。这与设计文档中"完整回测"的目标严重不符。

**建议**: `_process_single_day` 应遍历所有 candidates，为每条 recommendation 生成独立的 `BacktestTradeRecord`，并汇总到当日结果中。

---

#### D2: `RuleValidationResult` 为 frozen dataclass，但代码试图修改其字段【已修复】

```python
# src/backtest/engine.py:83-84
validation_result.trader_id = trader_id
validation_result.strategy_version_id = version_id
```

**问题**: `RuleValidationResult` 定义为 `@dataclass(frozen=True)`，上述赋值会在运行期抛出 `FrozenInstanceError`。当前单元测试未覆盖 `validate_rules_for_trader` 的完整路径，因此该 bug 未暴露。

**建议**: 取消 `frozen=True`，或在构造 `RuleValidationResult` 时一次性传入所有字段。

---

#### D3: `BacktestTradeRecord.entry_date/exit_date` 类型与赋值不匹配【已修复】

```python
# src/backtest/schemas.py:70-71
entry_date: date | None = None
exit_date: date | None = None

# src/backtest/engine.py:294-295
entry_date=trade_date.isoformat(),   # str!
exit_date=exit_date_str,             # str!
```

**问题**: schema 声明为 `date | None`，但 engine 赋值为 `str`。这会导致序列化/反序列化混乱，也与 `BacktestRequest` 中使用 `date` 类型不一致。

**建议**: 统一将 `entry_date`/`exit_date` 改为 `str`（与 scoring 返回值保持一致），或在 engine 层转换为 `date` 对象后再赋值。

---

### 3.2 中等缺陷（影响健壮性或准确性）

#### D4: `validate_rule_hits` 仅做字段存在性检查，未做真正的规则条件判断【已修复】

```python
# src/backtest/engine.py:361-364
for field in rule_meta.required_fields:
    if field in symbol_indicators:
        found = True
        break
```

**问题**: 规则 "rsi < 30" 被标记为命中，只要 `indicators` 中有 `rsi` 字段即可，**完全不检查数值是否小于 30**。这导致 hit/miss 统计失去意义。

**建议**: 对 `fully_programmable` 规则，至少实现简单的数值比较（如 `rsi < 30`、`macd > 0`）。对于无法解析的复杂条件，应降级为 `partially_programmable`。

---

#### D5: `cli/backtest.py` 的 `run_backtest` 未注入实际依赖【已修复】

```python
# cli/backtest.py:57
engine = BacktestEngine()
```

**问题**: `BacktestEngine()` 未传入 `loader` 和 `strategy_loader`，运行后所有记录都会是 `skipped` 状态。CLI 虽能跑通，但无实际业务价值。

**建议**: 在 CLI 中根据配置初始化 `SnapshotLoader`（绑定 `snapshot_service` 和 `strategy_repo`），再注入引擎。

---

#### D6: `is_trade_date` 未考虑 A 股法定节假日【已修复】

```python
# src/backtest/engine.py:91-93
def is_trade_date(d: date) -> bool:
    return d.weekday() < 5
```

**问题**: 仅跳过周末，未跳过春节、国庆、元旦等 A 股法定节假日。这会导致回测在休市日产生无效记录。

**建议**: 接入 `akshare` 交易日历或本地交易日历缓存，替换简单的 `weekday < 5` 判断。

---

#### D7: `classify_rule` 的正则匹配过于宽泛，易误判【已修复】

```python
# src/backtest/rule_registry.py:34
"ma": re.compile(r"(?<![a-zA-Z])ma\d*(?![a-zA-Z0-9])|(?<![a-zA-Z])ema\d*(?![a-zA-Z0-9])", re.IGNORECASE)
```

**问题**: `"market"` 中的 `"ma"` 会被匹配为均线指标；`"max_volume"` 也可能被误匹配。这会导致纯描述性规则被错误分类为 `fully_programmable`。

**建议**: 收紧正则边界，或在匹配后增加白名单/黑名单校验。

---

#### D8: `RuleValidationResult.posterior_return_*` 永远为 `None`【已修复】

```python
# src/backtest/engine.py:validate_rule_hits()
# 完全没有计算 posterior_return_mean / posterior_return_median 的逻辑
```

**问题**: `NTL-S6-011` 要求输出"命中后验收益分布"，但 `validate_rule_hits` 和 `validate_rules_for_trader` 均未计算该值。`reporting.py` 的模板虽有显示逻辑，但数据永远为空。

**建议**: 在 `validate_rule_hits` 中，对 hit 的样本计算后续 N 日收益（如 T+1/T+3/T+5），并填充 posterior 字段。

---

### 3.3 轻微缺陷（代码质量/风格）

#### D9: `SnapshotLoader.load_market_context` 中变量重复定义【已修复】

```python
# src/backtest/snapshot_loader.py:64,78,95
bars_by_symbol: dict[str, list[dict]] = {}    # 第64行
bars_by_symbol: dict[str, list[dict]] = {}    # 第78行（在 try 块内重复定义）
```

**问题**: 同一函数内同名变量多次注解赋值，虽不影响运行，但降低可读性。

**建议**: 统一初始化，避免重复声明。

---

#### D10: `BacktestEngine.run_sync` 在已有 event loop 中调用会失败【已修复】

```python
def run_sync(self, request: BacktestRequest) -> BacktestResult:
    return asyncio.run(self.run(request))
```

**问题**: 若已在异步环境（如 Jupyter、async CLI）中调用 `run_sync`，`asyncio.run` 会抛出 `RuntimeError`。

**建议**: 提供纯同步接口，或使用 `asyncio.get_event_loop().run_until_complete()` 做兼容处理。

### 4.2 串联问题

#### C1: `MarketContextSnapshot` 未定义为正式类型【已修复】

设计文档中定义了 `MarketContextSnapshot(TypedDict)`，但代码中 `SnapshotLoader.load_market_context` 返回的是普通 `dict[str, Any]`。这导致：
- 类型检查器（如 mypy）无法约束字段访问
- 下游模块（`engine`、`execution`）对 context 的字段访问无类型保障

**修复**: `schemas.py` 中新增 `MarketContextSnapshot(TypedDict)`，`snapshot_loader.py`、`execution.py`、`engine.py` 均已替换为 `MarketContextSnapshot` 类型。

---

#### C2: `BacktestRequest` 选型为 dataclass 而非 Pydantic【已修复】

设计文档明确要求使用 Pydantic BaseModel（用于请求校验、JSON 序列化、字段约束），但实现使用了标准库 `dataclass`。这导致：
- 缺少自动校验（如 `date_from <= date_to`）
- CLI 层需要手动解析和校验参数

**修复**: `BacktestRequest` 已迁移至 Pydantic `BaseModel`，新增 `@model_validator(mode="after")` 校验 `date_from <= date_to`，非法时抛出 `ValidationError`。

---

#### C3: `StrategyVersion.rules_snapshot` 的 `list[dict]` 类型过于松散【已修复】

`rules_snapshot` 在 Stage 3 中定义为 `list[dict]`，Stage 6 的 `rule_registry.py` 需要从中提取 `rule_id`、`condition`、`text` 等字段。由于 dict 结构无约束，字段缺失时 `classify_rule` 只能使用 `.get()` 兜底。

**修复**: `schemas.py` 中新增 `RuleSnapshot(TypedDict, total=False)`，包含 `rule_id`、`condition`、`text` 等字段；`rule_registry.classify_rule` 参数类型已更新为 `RuleSnapshot`。
