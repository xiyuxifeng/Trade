#### 缺陷 8：置信度计算函数存在但未被调用 ✅ 新发现

**问题：** `src/rule_backtest/confidence.py` 中实现了复杂的 `compute_confidence_adjustment()` 函数（多指标综合评分 + 贝叶斯更新），但 `RulePoolRepository.update_backtest_result()` **完全未使用**此函数，而是使用了简单的加权公式。

**confidence.py 实现的算法（正确的）：**
```python
# 多指标评分：胜率 35% + 盈亏比 30% + 夏普 20% + 回撤 15%
composite_score = (hit_rate_score * 0.35 + profit_loss_score * 0.30 + sharpe_score * 0.20 + drawdown_score * 0.15)
# 贝叶斯式加权更新
posterior = (prior_weight * initial_confidence + total_trades * protected_score) / (prior_weight + total_trades)
```

**repository.py 实际使用的公式（简化版）：**
```python
# repository.py:179-180
sample_weight = min(sample_count / 100.0, 1.0)
validated_confidence = initial_confidence * sample_weight + hit_rate * (1 - sample_weight)
```

**影响：**
- `confidence.py` 中的完整算法（胜率+盈亏比+夏普+回撤）**从未被执行**
- 即使实现了真正的回测，置信度调整仍然使用简化公式，与设计文档不符
- 代码冗余：`compute_confidence_adjustment()` 函数存在但无实际作用

**位置：** `src/rule_pool/repository.py:174-181`

### 3.2 中等缺陷

#### 缺陷 5：置信度调整权重与设计文档不一致 ✅ 已验证

**设计文档（设计.md:632-637）：**
```python
score = (
    0.4 * hit_rate +                    # 胜率权重 40%
    0.2 * min(profit_loss_ratio, 1.5) / 1.5 +  # 盈亏比权重 20%

```

**实际实现（confidence.py:77-82）：**
```python
composite_score = (
    hit_rate_score * 0.35 +      # 胜率权重 35%

    sharpe_score * 0.20 +        # 夏普权重 20%
    drawdown_score * 0.15        # 回撤权重 15%
)
```

虽然调整后的权重更合理（胜率+盈亏比合计 65%），但与设计文档明确记录不符，且未在文档中说明变更原因。

## 4. 串联性分析

### 4.1 数据流串联

```
文章
  ↓
article_classifier → meta.article_type ✅
  ↓
extract_article_metadata → meta.strategy_rules ✅（但不受 article_type 影响）
  ↓
[规则未自动入库] ❌
  ↓
[需要手动 CLI 入库]
  ↓
rule_pool 表 ← 手动或 CLI 写入 ⚠️
  ↓
run_rules_backtest → 使用模拟数据 ❌
  ↓
update_backtest_result → 计算 validated_confidence ✅
  ↓
[高置信度规则未进入预测] ❌
```

**串联状态：**
- ✅ 文章 → 分类：正常
- ✅ 分类 → 提取：正常（设置 article_type，但不影响后续）
- ❌ 提取 → 规则池：规则没有自动进入
- ⚠️ 规则池 → 回测：框架完成，但使用模拟数据
- ✅ 回测 → 置信度：计算逻辑正确
- ❌ 置信度 → 盘前预测：Stage 11 设计的"基于 rule_pool 高置信度规则生成预测"完全未实现

### 4.2 关键断裂点

1. **提取后不入库**：文章提取的规则存储在 `article_metadata.strategy_rules`，但不会自动创建 `rule_pool` 条目
2. **回测不验证规则**：调用 `run_rules_backtest` 但使用模拟数据，无法验证规则真实表现
3. **置信度无意义**：基于模拟回测计算的置信度不能反映规则真实性能
4. **预测缺失**：Stage 11 设计的基于 `rule_pool` 的盘前预测未实现，无法验证高置信度规则的实际预测效果

**说明：** 现有 `PreMarketService`（Stage 4）使用 `article_metadata.strategy_rules` → `StrategyVersion.rules_snapshot` 生成交易想法。这与 Stage 11 设计的"基于 `rule_pool` 表的 `validated_confidence >= 0.8` 规则生成预测"是**不同的路径**，两者未打通。

## 5. A 股市场适配性

### 5.1 符合 A 股特点的设计

| 特性 | 实现情况 |
|------|---------|

### 5.2 需要改进的地方

1. **涨停股买入限制未建模**
   - A 股涨停股次日可能继续涨停，但追高买入会失败
   - 回测应考虑涨停日不能买入的约束

2. **市值因子缺失**
   - A 股小市值因子显著，但指标库没有市值相关字段

3. **行业板块效应**
   - 规则触发应考虑板块联动，但当前设计是独立的标的规则

4. **财报发布窗口**
   - A 股财报季（4/8/10 月）会有"财报雷"，规则应考虑财报日历

## 7. 总结

### 7.1 整体评价

Stage 11 实现了一个**基础框架**，建立了：
- ✅ 规则池的数据模型（3 张表）
- ✅ 文章分类器
- ✅ DSL 映射工具
- ✅ 置信度计算逻辑
- ✅ 回测调度框架
- ✅ CLI 命令

但存在**三个核心断裂**：
1. **提取 vs 入库**：规则提取后不会自动进入 rule_pool
2. **回测 vs 模拟**：回测框架使用硬编码模拟数据
3. **置信度 vs 真实**：基于模拟数据的置信度无意义

### 7.2 风险评估

| 风险 | 等级 | 说明 |
|------|------|------|
| 回测使用硬编码数据 | **高** | 置信度不可信，可能导致错误决策 |
| 分层提取未实现 | **高** | 混合型文章无法正确处理 |
| 规则无法自动入库 | **高** | 无法形成闭环 |
| article_type 未持久化 | **中** | 分类结果无法追溯 |
| 盘前预测缺失 | **中** | 无法验证规则池价值 |

### Phase 1：数据流基础（提取 → 持久化 → 入库）

**目标：** 打通「文章提取 → 分类持久化 → 规则入库」的数据流

| 顺序 | Issue | 问题 | 依赖 | 说明 |
|------|-------|------|------|------|
| 1 | #3 | 分类结果未持久化 | 无 | 保存 article_classification 表，是后续分层提取的数据基础 |
| 2 | #9 | article_metadata 扩展字段从未填充 | #3 | standalone_rule_ids、trade_sample_ids 等字段需要被填充 |
| 3 | #2 | 分层提取未实现 | #3 | 根据 article_type（已设置）分发到不同提取逻辑 |
| 4 | #4 | 规则无法自动入库 | #2, #9 | 提取完成后自动创建 rule_pool 条目 |

**为什么 #3 必须最先修复：**
- 分类结果未持久化 → article_classification 表永远为空
- 后续分层提取需要查询历史分类结果来做质量控制
- 没有持久化就没有可追溯性

**为什么 #9 在 #3 之后：**
- extract_article_metadata.py 中需要同时写入 article_classification 和填充扩展字段
- 可以在同一处代码中一并处理

**为什么 #2 在 #3 和 #9 之后：**
- 分层提取需要先知道 article_type（#3 的输出）
- 同时需要填充 standalone_rule_ids 等字段（#9 的输出）
- 修复 #2 时，#3 和 #9 应该一并处理（或至少在同一次 commit 中）

**为什么 #4 在 #2 之后：**
- 规则自动入库需要先有完整的提取逻辑
- mapped_condition 必须已经生成（分层提取的输出）
- 否则入库的规则数据不完整

### Phase 2：回测核心（真实回测 + 置信度计算）

**目标：** 实现基于真实市场数据的回测，使用完整的置信度计算算法

| 顺序 | Issue | 问题 | 依赖 | 说明 |
|------|-------|------|------|------|
| 5 | #1 | 回测使用硬编码 60% 命中率 | #4 | 必须先有真实规则数据（rule_pool 中有真实 mapped_condition）才能做真实回测 |
| 6 | #8 | 置信度计算函数存在但未被调用 | #1 | 必须先有真实回测结果（样本数、胜率、夏普等），compute_confidence_adjustment() 才能正确执行 |

**为什么 #1 必须先于 #8：**
- #8 的 compute_confidence_adjustment() 需要真实的 total_trades、hit_rate、sharpe_ratio、max_drawdown
- 这些数据只能从真实回测中获得
- 在模拟数据上调用 compute_confidence_adjustment() 没有意义

### Phase 3：审核与置信度

**目标：** 完成 review_status 自动审核流程，对齐设计文档的置信度权重

| 顺序 | Issue | 问题 | 依赖 | 说明 |
|------|-------|------|------|------|
| 7 | #10 | review_status 审核流程未实现 | #4, #1 | 自动审核依赖规则已进入 rule_pool（#4）且有回测数据（#1） |
| 8 | #5 | 置信度权重与设计文档不一致 | #8 | 只有在 compute_confidence_adjustment() 被调用后，调整权重才有意义 |

**为什么 #10 在 Phase 1 + Phase 2 之后：**
- 自动审核逻辑需要 rule_pool 中已有数据
- 需要判断 initial_confidence >= 0.7 来决定是否自动通过
- 但初始置信度来自提取时的评估，不需要回测数据
- 所以实际上 #10 可以在 #4 之后、#1 之前执行（规则入库后立即做自动审核）
- 但考虑到审核通过后可能需要立即触发回测，归为 Phase 3 更合理

**为什么 #5 在 #8 之后：**
- 如果 compute_confidence_adjustment() 从未被调用，调整它的权重没有意义
- 先让正确的函数被调用，再对齐权重

### Phase 4：高级功能

**目标：** 实现基于规则池的盘前预测和盘后归因

| 顺序 | Issue | 问题 | 依赖 | 说明 |
|------|-------|------|------|------|
| 9 | #7 | 盘前预测/盘后归因缺失 | #1, #8, #10 | 盘前需要高置信度规则（#10），盘后需要真实回测数据（#1 #8） |
| 10 | #6 | article_id 类型不匹配外键 | 无 | 模型层面的类型修正，不影响数据流，可以在任何阶段执行 |

**为什么 #7 在所有其他问题之后：**
- 盘前预测需要 rule_pool 中 validated_confidence >= 0.8 的规则
- 这意味着 #1、#8、#10 都必须先完成
- 盘后归因需要当日预测信号与实际走势对比
- 这是端到端闭环的最后一步

**#6 的处理：**
- 类型不匹配是历史遗留问题，影响相对较小
- 可以在任何阶段修复，建议在 #4 之后、#1 之前的某个空隙执行
- 或者作为技术债务，在 Phase 4 结束时统一处理

### 修复风险提示

1. **Phase 1 期间回测会失败** — 因为 rule_pool 为空，run_rules_backtest 找不到规则
   - 解决方案：准备测试用历史数据，或在 Phase 1 末期用 CLI 手动导入一批规则

2. **Phase 2 回测结果会暴露之前被掩盖的问题** — 真实回测可能出现各种边界情况
   - 解决方案：预留 2-3 天 buffer 处理意外边界

3. **#8 和 #5 的权重调整可能需要同步修改** — 两者都与 confidence.py 有关
   - 建议在同一次 commit 中处理，避免重复修改同一文件

4. **#7 盘前/盘后归因是完全新增模块** — 可能需要补充设计文档
   - 建议先补充 design 再实现，避免返工
