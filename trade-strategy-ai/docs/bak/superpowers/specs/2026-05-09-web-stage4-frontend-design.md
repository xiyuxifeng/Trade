# Web Stage 4 前端设计文档

> 本文档用于定义 `trade-strategy-ai` 在 Stage 4 的 Web 前端基线方案。目标不是一次性做完所有页面，而是先建立一个可持续扩展的控制台骨架，使后续功能可以围绕同一套导航、布局、数据契约和视觉语言推进。

## 1. 设计目标

### 1.1 核心目标

- 建立一个面向交易策略研发与运营的 Web 控制台。
- 将现有 CLI 能力、API 能力和配置能力统一到同一套前端入口。
- 优先支持“查看状态、发起任务、追踪结果、下载产物、排查失败”这类高频操作。
- 为后续 Stage 5 及之后的盘前、盘后、回测、优化、运维页面打好基础。

### 1.2 设计边界

- 不把 Web 做成纯“配置表单后台”。
- 不把页面按代码模块组织，而是按用户任务组织。
- 不要求 Stage 4 一次性覆盖所有业务页面，只要求能形成稳定的前端主骨架。
- 不把长任务直接放在页面本身执行，所有长任务统一进入 Job Center。

## 2. 设计原则

### 2.1 任务优先

页面不是按照 `API` 名称分组，而是按照用户要完成的任务分组。用户进入 Web 后，首先看到的是“现在系统是否正常、有什么任务在跑、失败了什么、产物在哪里看、下一步该做什么”。

### 2.2 状态优先

所有关键页面都必须显式呈现以下状态：

- `loading`
- `empty`
- `success`
- `failed`
- `blocked`
- `needs confirmation`

高风险操作不能只靠 toast 提示，必须提供摘要、确认与结果回溯。

### 2.3 证据优先

每个结果页面都要能回到：

- 对应的 Job
- 对应的配置项
- 对应的日期或批次
- 对应的产物文件
- 对应的策略版本或市场快照

### 2.4 统一入口

Web 前端优先对接已经存在的 UI BFF：

- `/api/ui/v1/system/status`
- `/api/ui/v1/jobs*`
- `/api/ui/v1/workflows*`
- `/api/ui/v1/artifacts*`
- `/api/ui/v1/market*`

后续再逐步接入业务 API：

- `reports`
- `snapshots`
- `strategy_versions`
- `backtest_results`
- `rankings`
- `alerts`

### 2.5 权限与高风险边界

- 普通浏览操作与高风险操作必须在 UI 上区分开。
- `viewer / operator / admin` 的权限边界应在页面层显式体现，尤其是任务发起、配置保存、迁移、备份和恢复。
- 高风险操作必须展示摘要、影响范围和二次确认入口。
- 如果权限不足，页面应显示明确的拒绝原因，而不是空白或通用错误。

## 3. 推荐技术栈

### 3.1 基础技术

- `Vite`
- `React`
- `TypeScript`
- `React Router`

### 3.2 UI 与样式

- `Tailwind CSS`
- `shadcn/ui`
- `lucide-react`
- `clsx`
- `tailwind-merge`

### 3.3 数据与表单

- `TanStack Query`
- `Zod`
- `React Hook Form`
- `dayjs`

### 3.4 选择理由

- `Vite` 适合快速启动与快速迭代。
- `React + TypeScript` 适合未来承载复杂工作台和更多页面。
- `Tailwind + shadcn/ui` 适合高密度后台，组件一致性高，定制成本低。
- `TanStack Query` 适合任务状态、列表、详情、轮询和缓存。
- `Zod + React Hook Form` 适合配置保存、任务参数和高风险确认表单。

## 4. 目录结构设计

### 4.1 顶层结构

```txt
web/
├── package.json
├── vite.config.ts
├── tsconfig.json
├── tailwind.config.ts
├── postcss.config.js
├── components.json
├── index.html
└── src/
    ├── main.tsx
    ├── app/
    ├── layouts/
    ├── pages/
    ├── features/
    ├── components/
    ├── lib/
    ├── hooks/
    ├── types/
    ├── styles/
    └── assets/
```

### 4.2 目录职责

- `src/app/`：应用级入口、路由、Query Client、全局 Provider。
- `src/layouts/`：页面壳、布局容器、导航容器。
- `src/pages/`：路由页面。
- `src/features/`：按业务域组织的功能模块。
- `src/components/ui/`：基础 UI 原子组件。
- `src/components/layout/`：侧边栏、顶部栏、页头、状态条等布局组件。
- `src/components/status/`：状态卡片、健康标签、数据健康等跨页面组件。
- `src/lib/api/`：所有 HTTP 请求封装。
- `src/types/`：前后端数据契约类型。
- `src/styles/`：全局样式与主题变量。

### 4.3 拆分原则

- 页面负责路由和组合。
- feature 负责业务逻辑聚合。
- ui 负责纯展示组件。
- api 负责请求细节和错误归一。
- types 负责接口契约。

这样做的目的是避免后期把单个文件堆成“大杂烩”，同时也便于后续扩展更多业务区块。

## 5. 视觉与信息架构

### 5.1 视觉方向

前端视觉定位为“数据密集型金融分析控制台”，不是营销型 SaaS 页面。

建议风格：

- 中性深浅灰底色
- 强状态色
- 低装饰、高信息密度
- 表格优先于卡片堆叠
- 抽屉优先于复杂跳转

### 5.2 视觉目标

- 一眼看懂系统是否可用。
- 一眼看懂任务是否在跑。
- 一眼看懂任务卡在哪一步。
- 一眼找到产物、日志和下载入口。
- 一眼识别高风险操作。
- 桌面端保持高信息密度，移动端保留可用的最小操作路径。

### 5.3 信息层级

页面信息从高到低建议是：

1. 当前状态和进度
2. 当前任务
3. 关键结果
4. 证据和产物
5. 历史记录
6. 配置与运维

### 5.4 状态组件

全站统一状态表达，建议至少包含：

- `运行中`
- `成功`
- `失败`
- `待处理`
- `已阻塞`
- `需要确认`

这些状态不要只写文本，建议配颜色、图标和可操作按钮。

## 6. 导航结构

### 6.1 主导航

建议按用户任务组织导航，而不是按后端模块命名：

- 总览
- 任务中心
- 工作流
- 产物中心
- 市场数据
- 策略版本
- 回测中心
- 盘前工作台
- 盘后评估
- 系统设置
- 运维中心

其中 `策略版本 / 回测中心 / 盘前工作台 / 盘后评估 / 系统设置 / 运维中心` 在 Stage 4 中先作为占位入口保留，后续 Stage 5 及以后再逐步补齐功能。

### 6.2 导航设计原因

- 总览用于回答“系统现在是否正常”。
- 任务中心用于回答“任务怎么发起、怎么查看、怎么取消”。
- 工作流用于回答“盘前/盘后如何一键跑通”。
- 产物中心用于回答“结果在哪里、怎么追溯”。
- 市场数据用于回答“当前快照和行情在哪里”。
- 策略版本用于回答“每个 trader 当前是什么版本”。
- 回测中心用于回答“规则是否可复现、是否有效”。
- 盘前/盘后用于承接后续 Stage 4 之后的主流程升级。
- 系统设置和运维中心用于承接配置、迁移、备份、恢复、告警等高风险能力。

### 6.3 导航原则

- 先放高频任务，再放低频运维。
- 高风险入口放在显眼但有确认感的位置。
- 不能把导航做成 API 树。
- 不能把导航做成代码目录树。
- 桌面端以侧边栏为主，移动端以折叠抽屉或底部收纳为主，不能让主导航在小屏上完全失效。

## 7. 区块功能设计

### 7.1 总览

总览页是全站首页，必须展示：

- 系统状态
- 运行模式
- 数据库状态
- 配置文件路径
- 关键目录健康状态
- 最近 Job
- 最近产物
- 最近告警或失败记录

对应现有 UI BFF：

- `GET /api/ui/v1/system/status`
- `GET /api/ui/v1/jobs`
- `GET /api/ui/v1/artifacts`

### 7.2 任务中心

任务中心用于管理长任务与短任务的统一执行入口，必须支持：

- 创建任务
- 查看任务列表
- 查看任务详情
- 查看任务日志
- 取消任务
- 参数校验
- 执行结果回溯

对应现有 UI BFF：

- `GET/POST /api/ui/v1/jobs*`

CLI 映射示例：

- `crawl`
- `pipeline-run`
- `pipeline-step`
- `snapshot build`
- `strategy build`
- `backtest run`

### 7.3 工作流

工作流页用于把多步骤链路包装成用户可理解的操作向导，重点是：

- 盘前一键执行
- 盘后一键执行
- 状态追踪
- 结果摘要
- 失败重试入口

对应现有 UI BFF：

- `GET/POST /api/ui/v1/workflows*`

CLI 映射示例：

- `run-pre-market`
- `run-after-close`

### 7.4 产物中心

产物中心用于统一查看和追溯可展示的输出文件，必须支持：

- 产物列表
- 产物详情
- 预览
- 下载
- 按日期、类型、来源过滤

对应现有 UI BFF：

- `GET /api/ui/v1/artifacts*`

设计约束：

- 默认不索引敏感配置备份目录。
- 产物必须能够追溯到任务、日期和来源。

### 7.5 市场数据

市场数据页用于查看当前可用行情与标的集合，必须支持：

- symbol 列表
- OHLCV 查询
- 日期区间过滤
- 无数据空状态

对应现有 UI BFF：

- `GET /api/ui/v1/market/symbols`
- `GET /api/ui/v1/market/ohlcv`

CLI 映射示例：

- `ohlcv crawl`

### 7.6 策略版本

策略版本页用于查看每个 trader 的版本状态，必须支持：

- 策略版本列表
- 版本详情
- 版本下载
- trader 过滤
- 状态过滤

后续可逐步接入：

- `strategy_versions`
- `reports`

CLI 映射示例：

- `strategy build`
- `strategy list`

### 7.7 回测中心

回测中心用于查看和触发回测、规则验真和复现检查，必须支持：

- 发起回测
- 回测结果列表
- 回测报告查看
- 规则验真
- 可复现性检查

后续可接入：

- `backtest_results`
- `rankings`

CLI 映射示例：

- `backtest run`
- `backtest report`
- `backtest validate-rules`
- `backtest reproducibility-check`

### 7.8 盘前工作台

盘前工作台要面向“交易日开始前的决策准备”，建议呈现：

- 市场快照概览
- 热点题材
- 强势标的
- trader 维度建议
- 证据引用
- 盘前 Job 状态

这是后续 Stage 4 到 Stage 5 之间的关键承接页面。

### 7.9 盘后评估

盘后评估页要面向“复盘和归因”，建议呈现：

- 统一评分结果
- ranking
- 失败归因
- Evidence Pack
- postmortem
- 写回状态

### 7.10 系统设置

系统设置页只承载真正会影响运行的配置项，例如：

- `run_mode`
- `schedule.enable`
- `schedule.pre_market_time`
- `schedule.after_close_time`
- `api.auth.enabled`
- `evaluation.min_expected_return`
- `evaluation.loss_trigger`
- `evaluation.trade_constraint.*`
- `data.providers`
- `data.mock_prices`
- `persona.enable`
- `llm.provider / model / url`
- `kaipan.fetch_schedule`
- `akshare.*`

设计约束：

- 密钥类字段默认不明文展示。
- 高风险配置保存必须二次确认。
- 保存动作必须可审计。

### 7.11 运维中心

运维中心承载低频但高风险的能力：

- 数据库检查
- 数据库迁移
- 备份
- 恢复
- 调度状态
- 告警历史

这类能力必须有清晰确认步骤，不应被普通操作混在一起。

## 8. 与现有 API、CLI、配置的映射

### 8.1 API 映射

Stage 4 前端优先消费已落地的 UI BFF：

- 系统状态
- 任务中心
- 工作流
- 产物中心
- 市场数据

这能保证前端先稳定连上已经存在的接口，不会被后端未完成模块阻塞。

### 8.2 CLI 映射

前端页面应尽可能和已有 CLI 行为保持同义关系，常见映射包括：

- `crawl` -> 数据管道
- `run-pre-market` -> 盘前工作台
- `run-after-close` -> 盘后评估
- `strategy build` -> 策略版本
- `backtest run` -> 回测中心
- `ohlcv crawl` -> 市场数据
- `snapshot build` -> 产物 / 快照中心

这样用户从 CLI 迁移到 Web 时，不需要重新理解系统语义。

### 8.3 配置映射

Web 只展示对业务有实际意义的配置，不把所有 YAML 项无差别暴露出来。原则是：

- 可运行配置可见
- 高风险配置可控
- 密钥配置脱敏
- 保存动作可追踪

## 9. 首批页面与模块划分

### 9.1 首批页面

Stage 4 第一批建议实现：

- 总览
- 任务中心
- 工作流
- 产物中心
- 市场数据

### 9.2 首批组件

建议先落这些通用组件：

- 侧边栏
- 顶部栏
- 页头
- 状态条
- 指标卡
- 健康标签
- 表格
- 抽屉
- 弹窗
- toast
- 空状态
- Skeleton

### 9.3 首批功能模块

- 系统状态展示
- Job 列表和详情
- 工作流入口
- 产物列表和预览
- 市场 symbol 和 OHLCV 查询

## 10. 错误处理与空状态

### 10.1 错误处理

所有 API 错误都要统一展示，不能只在控制台报错。建议至少区分：

- 网络失败
- 授权失败
- 参数错误
- 服务端异常
- 业务拒绝

### 10.2 空状态

空状态不能只是“暂无数据”，而要告诉用户：

- 为什么没有数据
- 现在能做什么
- 去哪里继续

### 10.3 长任务状态

所有长任务必须呈现：

- 任务名称
- 提交时间
- 当前状态和进度
- 日志入口
- 结果入口
- 取消入口

### 10.4 首批页面验收口径

Stage 4 首批可用页面的最低验收标准如下：

- 总览页必须能展示系统状态、运行模式、数据库状态、配置路径、最近 Job 和最近产物。
- 任务中心页必须能查看 Job 列表，并进入详情和日志。
- 工作流页必须能看到可执行工作流入口，并能触发运行。
- 产物中心必须能查看、预览和下载产物。
- 市场数据页必须能按 symbol 和日期区间查询 OHLCV。
- 任意页面在 API 不可用时都必须给出可读的错误状态。

## 11. 非目标

Stage 4 不优先做以下内容：

- 全量复杂图表系统
- 完整的权限管理后台
- 多主题切换
- 大规模实时推送
- 自动交易入口

这些能力如果后续需要，可以在稳定骨架上逐步扩展。

## 12. 风险与注意事项

- 不要把页面做成 API 目录树。
- 不要把所有配置一次性暴露给前端。
- 不要把长任务直接嵌入页面逻辑。
- 不要让 `web/` 的目录失去业务边界。
- 不要让 Stage 4 变成“只有首页、没有任务闭环”的空壳。
- 不要把 Stage 4 的占位导航项误当成已完成页面。

## 13. 与 Stage 4 的关系

本设计文档是 Stage 4 的稳定设计基线。后续实施应优先遵循本设计，再按照实施计划逐步推进 `WEB-S4-001` 到 `WEB-S4-004`。
