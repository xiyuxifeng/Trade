# WEB-S7-008 角色权限模型设计

## 目标

为 Web 管理后台补齐最小角色权限模型，覆盖 `viewer / operator / admin` 三档权限，并同时把权限校验落到后端和前端。

本任务的核心要求是：

1. 后端必须强制校验权限，不能只靠前端隐藏按钮。
2. 前端必须感知当前角色，并据此隐藏或禁用无权限入口。
3. 角色必须可从现有 API Key 体系中推导出来，避免引入全新的用户系统。
4. 默认配置必须提供可直接用于本地验证的 API Key。

## 设计决策

### 1. 角色绑定到 API Key

当前项目没有完整用户表和登录系统，因此本阶段不新增独立用户体系，而是把角色绑定到 API Key。

角色定义如下：

- `viewer`：只读访问
- `operator`：可以执行非破坏性任务
- `admin`：可以执行配置保存、恢复、备份、数据库迁移等高风险操作

API Key 仍然是当前认证载体，但每个 key 额外携带一个 role。

### 2. 配置格式兼容旧格式

`api.auth.api_keys` 需要同时兼容两种写法：

- 旧格式：`["demo-key"]`
- 新格式：`[{ key: "demo-key", role: "admin", label: "Local Admin" }]`

兼容规则：

- 旧字符串格式默认视为 `admin`
- 新对象格式显式声明 `key` 和 `role`
- 统一在配置加载后归一化成结构化 principal 列表
- 配置模型本身也要支持这两种形态，不能只在认证函数里临时拼接

这样可以避免破坏现有配置，也便于逐步迁移。

### 3. 默认 API Key 分配

为满足本地开发和自动化测试，默认配置提供三把示例 key：

- `trade-strategy-ai-local-viewer`
- `trade-strategy-ai-local-operator`
- `trade-strategy-ai-local-admin`

其中 `trade-strategy-ai-local-admin` 作为默认管理 key。

这三把 key 仅用于本地默认配置和测试环境。生产环境必须覆盖为真实 key。

注意：

- 不要把可直接使用的默认 key 直接写入仓库运行态 `config/app.yaml`
- 默认 key 应主要出现在默认模板、初始化生成逻辑或本地示例配置中

## 后端设计

### 1. principal 抽象

新增一个统一的 principal 概念，用于表示当前请求身份：

- `anonymous`
- `viewer`
- `operator`
- `admin`

后端认证依赖从“只返回 API key 字符串”升级为“返回当前 principal”。

principal 至少包含：

- `role`
- `api_key_label`
- `authenticated`
- `source`（例如 header / anonymous）

### 2. 权限依赖

新增两个层级的依赖工具：

- `get_current_principal()`：解析当前身份
- `require_role(min_role)`：校验当前身份是否满足最小角色

角色比较规则：

- `anonymous < viewer < operator < admin`

后端所有 UI API 路由都需要显式声明最低权限。

### 3. 路由权限矩阵

建议的默认矩阵如下：

- `GET /api/ui/v1/auth/me`：viewer+
- `GET /api/ui/v1/jobs/*`：viewer+
- `POST /api/ui/v1/jobs`：operator+
- `POST /api/ui/v1/jobs/{id}/cancel`：operator+
- `GET /api/ui/v1/settings/*`：viewer+
- `POST /api/ui/v1/settings/save`：admin
- `POST /api/ui/v1/settings/restore`：admin
- `GET /api/ui/v1/settings/backups`：viewer+
- `GET /api/ui/v1/system/*`：viewer+
- `GET /api/ui/v1/ops/*`：admin

Job 定义里的 `permission` 仍然保留，由 Job Registry 继续控制 job 级别最小权限。路由权限是第一道门，job permission 是第二道门。

## 前端设计

### 1. 当前角色获取

前端新增一个轻量身份查询接口，启动时请求当前 principal。

前端保存的 API Key 仍然通过现有 `X-API-Key` header 传递，不新增登录表单。

### 2. 界面表现

前端根据 role 控制：

- 侧边栏导航入口可见性
- 页面内高风险按钮的禁用状态
- Settings 页面保存/恢复按钮
- Ops 页面危险操作按钮

推荐策略：

- `viewer`：只展示只读页面和只读操作
- `operator`：展示任务执行入口，但禁用高风险设置保存入口
- `admin`：完整可用

### 3. 体验约定

无权限入口优先采用“禁用并提示原因”，而不是完全隐藏。

原因：

- 用户更容易理解自己缺什么权限
- 测试更容易覆盖
- 后续扩展权限时不会频繁改动导航结构

## 默认 key 的使用方式

默认 key 只用于本地启动和测试。

建议配置示例：

```yaml
api:
  auth:
    enabled: true
    api_keys:
      - key: trade-strategy-ai-local-viewer
        role: viewer
      - key: trade-strategy-ai-local-operator
        role: operator
      - key: trade-strategy-ai-local-admin
        role: admin
```

如果用户仍然使用旧的字符串列表配置，系统会按 `admin` 处理，保持兼容。

## 错误处理

权限失败必须返回统一错误，前后端都可识别。

推荐错误语义：

- 403
- `insufficient permissions`

前端拿到 403 后应显示明确提示，例如“当前 API Key 仅具备 viewer 权限，无法执行保存配置”。

## 测试策略

### 后端

需要覆盖以下场景：

- `viewer` 可以访问只读接口
- `viewer` 不能提交 job
- `operator` 可以提交普通 job
- `operator` 不能保存 settings
- `admin` 可以保存和恢复 settings
- 默认字符串 key 仍可兼容旧配置
- `anonymous` 在开启鉴权时被拒绝

### 前端

需要覆盖以下场景：

- 不同角色下侧边栏和关键按钮的可见性/禁用状态
- Settings 保存/恢复按钮仅 admin 可用
- Jobs 创建入口仅 operator/admin 可用
- 角色查询失败时的降级提示

## 交付边界

本阶段只做最小角色权限模型，不引入：

- 用户表
- 密码登录
- session 刷新
- 复杂 RBAC 资源树

这些能力如果需要，应作为后续独立任务推进。
