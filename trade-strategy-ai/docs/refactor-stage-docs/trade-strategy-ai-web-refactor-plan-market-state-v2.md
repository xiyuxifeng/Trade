# Trade Strategy AI Web 重构方案

## 1. 文档目的

本方案用于将 `trade-strategy-ai` 从当前偏工程化、入口分散、流程不清晰的 Web 系统，重构为一个围绕以下业务闭环运行的可交付产品：

```text
文章研究
→ LLM 提取规则
→ 人工审核
→ 历史回测
→ 识别规则适用市场状态
→ 形成正式策略版本
→ 每日盘前生成交易计划
→ 每日盘后复盘成败原因
→ 生成规则、画像和策略优化建议
→ 审核后发布新版本
```

重构重点不是继续增加页面，而是解决以下问题：

1. 入口混乱。
2. 用户不知道完整流程。
3. 前后步骤衔接不畅。
4. 子页面职责重叠。
5. 每个功能输入和输出不明确。
6. 基础能力直接暴露，使用成本过高。
7. Job、Workflow、Artifact 等技术概念占据业务入口。
8. 策略、每日计划、规则选择和市场状态之间的关系不清晰。

---

# 1.1 术语统一

面向中国用户，本文档和未来 Web 界面统一使用 **“市场状态”** 表示英文概念 `Market Regime`。

推荐用户界面术语：

- Market Regime：市场状态
- Regime Label：市场状态标签
- Regime Confidence：市场状态置信度
- Regime Features：市场状态特征
- Regime-aware Backtest：分市场状态回测
- Regime-aware Rule Selection：基于市场状态的规则选择
- Regime Definition Version：市场状态模型版本

代码和数据库中可暂时保留既有 `regime` 字段，以避免无必要的大规模迁移；但 API 展示文案、Web 页面、用户文档和验收说明应统一使用“市场状态”。

# 2. 产品定位

系统应从：

```text
技术能力和任务执行门户
```

重构为：

```text
交易研究、策略管理和每日决策闭环产品
```

用户不需要理解底层的：

- Job
- Workflow
- Pipeline
- Artifact
- CLI 命令
- 文件路径
- `kaipan-fetch`
- `kaipan-normalize`
- `ohlcv-crawl`
- `market-state-build`

这些能力继续保留，但下沉为系统基础设施，只在运行详情、失败排查和系统管理中出现。

# 3. 核心设计原则

## 3.1 按业务流程组织，不按技术模块组织

页面和导航必须回答：

- 用户现在处于哪个阶段？
- 需要提供什么输入？
- 系统会执行什么？
- 会得到什么输出？
- 下一步应该做什么？

## 3.2 每个页面统一使用四段式结构

```text
输入
→ 处理状态
→ 输出
→ 下一步
```

## 3.3 日常业务与系统运维分离

普通用户日常主要使用：

- 首页
- 今日盘前
- 今日盘后

管理员和高级用户使用：

- 数据与调度
- Profile
- 任务运行
- 数据库与备份
- 权限和审计

## 3.4 正式策略与每日运行实例分离

正式策略相对稳定，不每天重建。

每天根据市场状态生成：

```text
Daily Rule Selection
+
Daily Strategy Instance
+
Trading Day Plan
```

只有在策略持续退化、规则结构变化或人工确认后，才发布新的正式策略版本。

## 3.5 所有核心对象必须版本化和可追溯

任何盘前计划都应能追溯到：

- 使用的数据快照
- 市场状态 版本
- 策略版本
- 交易员画像版本
- 规则版本
- 每日规则选择结果
- 执行 Job
- 输出 Artifact

# 4. 最终用户操作流程

## 4.1 首次建立策略

```text
导入文章
→ 系统清洗并调用 LLM 提取候选规则
→ 用户审核和修正规则
→ 系统自动检查并补齐回测数据
→ 运行全周期和分市场状态回测
→ 用户选择通过验证的规则
→ 生成策略草稿
→ 用户检查画像、规则、权重和风险参数
→ 发布正式策略版本
```

## 4.2 每个交易日盘前

```text
系统自动抓取 Kaipan 盘前数据
→ 标准化并冻结盘前快照
→ 判断今日市场状态
→ 加载当前正式策略
→ 从策略规则池中选择今日适用规则
→ 生成每日策略实例
→ 生成候选标的、信号和风险提示
→ 用户查看并批准今日计划
```

## 4.3 每个交易日盘后

```text
系统更新 OHLCV
→ 更新指标和收盘市场状态
→ 抓取 Kaipan 盘后数据
→ 对比盘前预测和实际结果
→ 分析成功和失败原因
→ 更新规则在不同市场状态下的表现
→ 生成画像、规则和策略优化建议
→ 用户接受、忽略或继续观察
```

## 4.4 策略更新

```text
发现持续退化或出现更优规则
→ 生成策略调整草稿
→ 自动回测和样本外验证
→ 用户审核
→ 发布新策略版本
```

# 6. 各模块设计

## 6.1 首页

首页是用户的下一步操作中心，而不是统计大屏。

### 首页需要回答

1. 今天数据是否就绪？
2. 今日盘前计划是否已生成？
3. 昨日盘后复盘是否完成？
4. 是否有规则等待审核？
5. 是否有失败任务或数据缺失？
6. 当前使用哪个策略版本？
7. 当前市场状态是什么？

### 首页结构

```text
今日状态
├─ Kaipan 盘前数据
├─ OHLCV 最新日期
├─ 当前市场状态
├─ 当前正式策略
├─ 今日规则选择
├─ 今日盘前计划
└─ 昨日盘后复盘

待办事项
├─ 候选规则待审核
├─ 回测结果待确认
├─ 优化建议待处理
├─ 数据异常
└─ 失败任务

最近结果
├─ 最新盘前计划
├─ 最新盘后报告
├─ 当前交易员画像
└─ 最新策略调整建议
```

首页状态必须直接跳转到对应处理页面。

负责从文章到候选规则。

```text
研究中心
├─ 文章库
├─ 添加文章
├─ 提取记录
└─ 候选规则
```

### 文章详情输入

- 原文
- 来源
- 作者
- 发布时间
- 标签
- 使用的 Profile
- 提取模板

### 文章详情输出

- 摘要
- 核心观点
- 候选规则
- 入场条件
- 退出条件
- 风险条件
- 引用证据
- LLM 推断说明

### 用户主要操作

```text
重新提取
审核候选规则
加入规则池
```

抓取、清洗、解析和 LLM 调用过程收纳进“运行详情”。

## 6.3 规则与回测

将规则池和回测整合为一个连续业务域。

```text
规则与回测
├─ 候选规则
├─ 正式规则
├─ 回测实验
└─ 规则比较
```

### 规则生命周期

```text
候选
→ 待审核
→ 已批准
→ 待回测
→ 验证中
→ 可用
→ 限定使用
→ 已停用
```

### 规则详情固定结构

```text

适用性

```

### 规则输入

- 入场条件

- 标的范围

### 规则输出

- 收益
- 胜率
- 最大回撤
- 盈亏比
- 交易次数
- 分市场状态表现
- 样本内和样本外表现
- 推荐状态

# 7. 规则适用市场状态设计

文章提取的规则允许没有初始适用条件。

## 7.1 四类适用性

```text
declared_applicability
文章或作者明确声明

inferred_applicability
LLM 根据语义推测，只作为假设

observed_applicability
通过分市场状态回测实际测得

approved_applicability
人工批准后用于生产
```

## 7.2 首次回测原则

如果文章未声明适用市场：

```text
所有市场状态开放运行
→ 按每日 市场状态 分组统计
→ 生成 observed_applicability
```

不能：

- 把未知直接视为适用全部市场。
- 把 LLM 推测直接当作正式约束。
- 只在 LLM 推测的市场状态中回测。

## 7.3 适用性状态

```text
unknown
insufficient_sample
enabled
observe
disabled
```

## 7.4 生产优先级

```text
approved_applicability
→ observed_applicability
→ 无充分证据时按策略风险模式处理
```

风险模式可以是：

- 保守：未知时不启用。
- 平衡：未知时低权重。
- 探索：未知时小仓位观察。

---

# 7.1 候选规则审核机制

候选规则不能由 LLM 直接转为正式规则，但也不应要求用户逐条审核全部规则。

采用：

```text
自动审核
+
人工审核
```

## 自动审核

系统自动检查：

- JSON 和 Schema。
- 原文证据。
- 条件和动作完整性。
- 模糊词和缺失参数。
- 退出、失效和持有周期。
- 市场状态是否明确声明。
- 数据依赖是否可用。
- 重复和冲突。
- 可回测性。
- LLM 置信度和风险等级。

自动审核输出：

```text
自动通过
建议通过
需要人工确认
不可回测
建议拒绝
```

自动通过只允许规则进入“待回测”，不能直接成为正式可用规则。

## 人工审核

人工主要处理：

- 规则存在歧义。
- 参数需要补充。
- 风险和仓位条件。
- LLM 推断市场状态。
- Kaipan 或复杂数据依赖。
- 重复或冲突。
- 准备进入正式策略。

人工操作：

```text
批准
修改后批准
合并
暂存
拒绝
```

规则准备进入正式策略前，必须再次人工确认回测结果和正式适用性。

## 审核 UI

审核工作台应显示：

- 规则内容。
- 原文证据。
- 自动审核结果和原因。
- 风险等级。
- 缺失信息和模糊条件。
- 数据依赖和可回测状态。
- 重复或冲突提示。
- 回测状态。

支持批量处理低风险规则，并保留完整审核审计记录。

# 8. 回测数据设计

## 8.1 回测主数据

OHLCV 是基础回测数据。

用于：

- 收益计算
- 技术指标
- 趋势判断
- 信号触发
- 基准比较
- 市场状态

## 8.2 首次回灌

首次部署时执行：

```text
股票池、指数和 ETF
→ 批量抓取历史 OHLCV
→ 写入数据库
→ 完整性检查
→ 计算指标
→ 生成历史 市场状态
```

建议：

- 主要指数：8～10 年。
- 股票：至少 5 年。
- 核心标的：尽量 8～10 年。
- 日线优先，分钟线后续扩展。

## 8.3 每日增量

```text
查询数据库最新交易日
→ 抓取后续交易日
→ upsert
→ 检查缺口
→ 更新指标
```

## 8.4 回测前自动检查

```text
标的数据是否完整
基准指数是否完整
指标是否生成
市场状态 是否生成
Kaipan 历史快照是否需要
```

缺失时由回测页面提供：

```text
自动补齐并开始回测
```

用户不需要先进入系统管理。

## 8.5 固定数据版本

每次回测必须记录：

- dataset_snapshot_id
- 数据日期范围
- 标的集合
- 数据质量状态
- benchmark
- market_state_definition_version
- Kaipan 快照覆盖率

# 9. Kaipan 在回测中的作用

## 9.1 基础回测不强制依赖 Kaipan

只使用以下条件的规则可仅用 OHLCV：

- 价格
- 成交量
- 均线
- MACD
- RSI
- 突破
- 回撤
- 波动率
- 指数趋势

## 9.2 以下规则需要 Kaipan 历史快照

- 热点题材
- 板块强度
- 涨停情绪
- 集合竞价
- 强势股池
- 封板质量
- 龙虎榜
- 风口
- 市场情绪
- 题材成分

## 9.3 回测分级

```text
Level 1：OHLCV
Level 2：OHLCV + 市场状态
Level 3：OHLCV + 市场状态 + Kaipan 历史快照
```

## 9.4 数据缺失处理

历史 Kaipan 不完整时：

- 不能把缺失条件当作 false。
- 不能默认为通过。
- 应标记为不支持验证或降级回测。
- 输出必须显示缺失数据及影响。

# 10. 市场状态 与规则绑定

## 10.1 每日 市场状态

核心字段：

```text
trade_date
benchmark_symbol
market_state_definition_version
market_state_label
confidence
feature_snapshot_id
```

市场状态 必须只使用当日及之前可获得的数据，禁止未来数据泄漏。

## 10.2 回测执行

```text
遍历每个交易日
→ 加载截至当日的数据
→ 加载或计算当日 市场状态
→ 执行规则
→ 按 市场状态 记录表现
```

## 10.3 RuleApplicabilityProfile

建议独立建模：

```text
rule_version_id
market_state_definition_version
market_state_label
sample_count
performance_metrics
recommendation
confidence
review_status
```

这样市场状态算法更新后，可以重新生成适用性画像，而无需修改规则本体。

# 11. 策略设计

## 11.1 正式策略版本

正式策略定义稳定边界：

```text
规则池
规则基础权重
交易员画像
风险策略
仓位限制
标的范围
规则选择政策
失效和降级政策
```

生命周期：

```text
草稿
→ 待验证
→ 已回测
→ 待审核
→ 已发布
→ 当前使用
→ 已归档
```

## 11.2 每日规则选择

每天自动执行：

```text
当前正式策略
+
今日 市场状态
+
Rule Applicability Profile
+
数据质量
=
Daily Rule Selection
```

输出：

- selected_rules
- reduced_weight_rules
- blocked_rules
- selection_reason
- confidence
- warnings

## 11.3 每日策略实例

每天生成的是每日实例，不是新的正式策略。

```text
strategy_version_id
trade_date
market_state_id
rule_selection_id
risk_multiplier
position_limit
candidate_pool_snapshot_id
```

## 11.4 生成新策略版本的触发条件

- 核心规则持续退化。
- 当前 市场状态 下长期没有可用规则。
- 多个规则连续被暂停。
- 新规则经过验证并显著优于旧规则。
- 交易员画像发生有效变化。
- 风险和仓位约束改变。
- 周期性策略审查。

新版本流程：

```text
触发异常
→ 生成调整建议
→ 形成策略草稿
→ 回测和样本外验证
→ 人工审核
→ 发布
```

不能自动覆盖当前正式策略。

# 12. 交易员画像设计

画像应为结构化、版本化对象。

## 12.1 画像内容

```text
交易风格
偏好市场和行业
持有周期
风险偏好
仓位习惯
止损止盈习惯
成功环境
薄弱环境
常见行为偏差
```

## 12.2 画像更新

盘后只生成画像变更建议。

必须显示：

- 更新前后差异
- 支撑证据
- 使用的交易案例
- 统计结论
- LLM 推断
- 置信度

用户确认后发布新的 TraderProfileVersion。

---


# 12.1 作者画像的定义与生成方式

本项目中的“画像”不是系统用户画像，而是 **文章作者的交易方法画像**。

它描述的是：

> 作者通常如何理解市场、选择标的、定义买卖点、控制风险，以及从其文章中提取出的规则在历史数据中实际表现如何。

由于系统没有作者的真实账户、成交记录或交割单，因此不能生成作者真实交易行为画像，也不能声称作者的真实胜率、收益率、最大回撤或执行习惯。

作者画像应拆分为三层。

## 12.1.1 作者方法画像

建议对象名称：

```text
AuthorMethodProfile
```

主要由 LLM 根据文章内容生成，包含：

- 交易风格。
- 市场分析框架。
- 选股偏好。
- 常用入场逻辑。
- 常用退出逻辑。
- 风险表达。
- 持有周期。
- 常用指标和市场数据。
- 可能适用的市场状态假设。
- 原文证据和置信度。

这部分反映的是作者在文章中表达的方法体系，属于内容理解结果，必须标记为“未验证”或“待验证”。

## 12.1.2 作者规则画像

建议对象名称：

```text
AuthorRuleProfile
```

主要通过程序统计作者名下已经提取、审核和标准化的规则生成，包含：

- 趋势类规则占比。
- 反转类规则占比。
- 题材类规则占比。
- 规则量化程度。
- 是否依赖 Kaipan 数据。
- 常见入场条件。
- 常见退出条件。
- 常见持有周期。
- 规则之间的一致性。
- 规则冲突和重复情况。
- 代表性规则族。

这部分不应完全依赖 LLM，可以通过规则字段、标签和指纹统计生成，LLM只负责解释和总结。

## 12.1.3 作者方法验证画像

建议对象名称：

```text
AuthorValidatedProfile
```

主要通过回测和每日运行统计生成，包含：

- 哪类规则表现最好。
- 哪类规则表现较弱。
- 经验证的优势市场状态。
- 经验证的弱势市场状态。
- 常见失效模式。
- 不同市场状态下的样本量。
- OHLCV 回测和 Kaipan 增强回测的差异。
- 文章表达是否得到数据支持。
- 当前证据强度和置信度。

它描述的是：

> 从作者文章中提取出的规则集合，在历史数据和每日运行中的实际表现。

它不是作者真实实盘表现。

## 12.1.4 作者画像的最终生成公式

```text
作者画像
=
LLM 内容理解
+
规则结构统计
+
回测与每日运行验证
```

LLM负责：

- 理解文章。
- 总结方法。
- 解释差异。
- 生成易读描述。

程序统计负责：

- 规则数量。
- 规则类型分布。
- 重复和冲突。
- 样本量。
- 表现指标。
- 证据聚合。

回测负责：

- 验证规则有效性。
- 验证市场状态适用性。
- 识别优势和弱势环境。
- 生成客观表现依据。

## 12.1.5 作者画像生成时机

初始画像建议在满足以下任一条件后生成：

```text
有效文章达到 3～5 篇
或
有效候选规则达到 10 条
```

生成：

- AuthorMethodProfile。
- AuthorRuleProfile。

完成第一轮规则回测后生成：

- AuthorValidatedProfile V1。
- 优势市场状态。
- 弱势市场状态。
- 有效规则类型。
- 样本不足项。

后续更新方式：

```text
新文章导入
→ 更新作者方法画像草稿

新规则审核通过
→ 更新作者规则画像草稿

新回测完成
→ 更新作者验证画像草稿

每日盘后
→ 累计证据，不立即发布新版本

达到样本阈值或定期审查
→ 生成新画像草稿

人工确认
→ 发布新画像版本
```

正式画像不应每天重建。

## 12.1.6 作者画像对盘前预测的作用

作者画像不能直接替代规则和回测结果。

盘前规则选择优先级应为：

```text
规则适用性回测结果
> 当前市场状态
> 当前正式策略
> 数据质量
> 作者验证画像
> 作者方法画像
```

作者画像主要用于：

- 组织作者规则池。
- 生成作者风格的策略模板。
- 为每日规则选择提供辅助权重。
- 判断当前市场是否匹配作者方法。
- 提高盘前结果解释性。
- 提供作者整体风险提示。

例如：

```text
作者方法画像：
偏好题材突破

作者验证画像：
题材活跃、成交放大时表现较好

今日市场状态：
题材活跃度低

结果：
降低该作者规则整体权重
```

## 12.1.7 盘后如何优化作者画像

盘后不是“优化作者”，而是：

> 校正系统对作者交易方法的理解。

盘后应先累计结构化证据：

- 今日启用规则数量。
- 实际触发规则数量。
- 成功和失败数量。
- 不同规则类型表现。
- 不同市场状态表现。
- 常见失败原因。
- 数据缺失和降级情况。

达到样本阈值后：

```text
结构化统计
→ 生成画像差异
→ LLM解释变化
→ 形成画像草稿
→ 人工审核
→ 发布新画像版本
```

如果作者不同阶段方法发生明显变化，应支持时间分段画像：

```text
作者画像 V1：早期低吸反转阶段
作者画像 V2：后期趋势突破阶段
```

不能把明显不同的方法强行平均成一个固定画像。

# 12.2 大规模文章处理方案

当前已有 100 多篇文章，数量足以生成较稳定的作者方法画像。

真正需要控制的不是文章数量，而是：

- 是否属于同一作者。
- 时间跨度。
- 重复内容。
- 方法阶段变化。
- 有效规则数量。
- 规则可量化程度。
- 历史数据可获得性。

禁止将全部文章全文一次性放入一个 LLM Prompt。

## 12.2.1 逐篇结构化

每篇文章独立处理：

```text
文章
→ 清洗
→ 摘要
→ 方法标签
→ 候选规则
→ 证据片段
→ 时间、主题和风格元数据
```

建议保存：

```json
{
  "article_id": "A-101",
  "published_at": "2024-03-12",
  "method_tags": ["趋势", "突破", "放量确认"],
  "holding_period": "1-5日",
  "risk_concepts": ["跌破均线止损"],
  "rule_ids": ["R-201", "R-202"],
  "evidence_refs": ["E-501", "E-502"]
}
```

后续画像生成优先读取结构化结果，不重复读取全部文章全文。

## 12.2.2 去重与聚类

按以下维度聚类：

- 交易风格。
- 入场逻辑。
- 持有周期。
- 市场类型。
- 题材或行业。
- 发布时间。
- 相似规则。
- 数据依赖。

例如：

```text
趋势突破类：32 篇
低吸反转类：18 篇
题材轮动类：27 篇
风险管理类：11 篇
其他或不可量化：19 篇
```

## 12.2.3 分层汇总

采用三层结构：

```text
单篇文章结果
→ 主题或时间段画像
→ 作者总画像
```

单篇层保存原始观点、规则和证据。

分组层按主题或时间段生成局部画像，例如：

```text
2022～2023：低吸反转方法
2024：题材短线方法
2025～2026：趋势突破方法
```

作者总画像只总结长期稳定特征，同时保留阶段差异。

## 12.2.4 Map-Reduce 处理方式

推荐：

```text
100 多篇文章全文
↓
逐篇生成结构化结果
↓
每 10～20 篇或每个主题生成局部摘要
↓
使用局部摘要、规则统计和关键证据生成作者总画像
```

禁止：

```text
100 篇全文
→ 一个超长 Prompt
→ 一次生成最终画像
```

原因：

- Token 成本高。
- 容易超出上下文。
- 重复内容稀释关键信息。
- 重要证据容易丢失。
- 无法精确追溯。
- 不利于增量更新。

## 12.2.5 增量更新

初始处理完成后，新文章进入时只处理增量：

```text
处理新文章
→ 判断所属聚类
→ 更新局部画像
→ 检查是否影响作者总画像
```

只有出现以下情况时才生成新的正式画像草稿：

- 新文章引入新的方法类型。
- 某个结论的证据显著增强。
- 与当前画像产生明显冲突。
- 作者方法发生阶段性变化。
- 新规则回测结果改变已有验证结论。

## 12.2.6 规则去重和规则族

不要对每篇文章中的每条规则直接独立回测。

推荐流程：

```text
100 多篇文章
→ 提取候选规则
→ 标准化
→ 规则指纹
→ 合并重复和高度相似规则
→ 形成规则族
→ 对标准规则和必要参数变体回测
```

规则指纹可以基于：

- 入场条件。
- 退出条件。
- 标的范围。
- 数据周期。
- 参数。
- 数据依赖。
- 持有周期。

建议对象：

```text
RuleFamily
├─ 标准规则
├─ 来源文章
├─ 参数变体
├─ 原文证据
└─ 规则版本
```

## 12.2.7 回测优先级

初期不需要回测所有规则。

### P0

- 多篇文章反复出现。
- 条件明确。
- 数据可获得。
- 容易量化。
- 代表作者核心风格。

### P1

- 重要但依赖 Kaipan。
- 需要复杂市场上下文。
- 参数存在一定模糊性。

### P2

- 单篇偶发观点。
- 高度主观。
- 无法获得历史数据。
- 无明确退出条件。

先使用 P0 规则生成第一版验证画像，再逐步补齐。

## 12.2.8 数据质量统计

系统应显示：

```text
文章总数
有效文章数
重复或低信息文章数
候选规则数
去重后规则族数
可直接回测规则数
依赖 Kaipan 规则数
暂不可量化规则数
```

例如：

```text
文章总数：126
有效文章：108
重复或低信息文章：18
提取候选规则：286
去重后规则族：57
可直接回测：34
依赖 Kaipan：15
暂不可量化：8
```

画像置信度应综合：

- 有效文章数量。
- 规则数量。
- 跨文章一致性。
- 时间覆盖。
- 原文证据数量。
- 回测样本量。
- 市场状态覆盖率。

不能只根据文章总数判断画像可靠性。

## 12.2.9 大规模数据处理结论

100 多篇文章已经足够。

推荐长期处理链路：

```text
逐篇结构化
→ 去重聚类
→ 分层汇总
→ 规则族合并
→ 优先级回测
→ 增量更新画像
```

长期事实源应为：

```text
文章原文
+
单篇结构化结果
+
去重后的规则版本
+
回测统计
+
作者画像版本
```

这样即使后续增长到几百或几千篇文章，成本和复杂度仍然可控。

# 23. 重构实施阶段

## Stage 0：产品契约和导航收口

目标：

- 定义六个主导航。
- 明确业务对象和状态。
- 定义页面输入输出契约。
- 将 Job、Workflow、Artifact 从主导航移除。
- 建立统一运行详情。
- 建立 legacy 路由映射和退出计划。

验收：

- 用户不接触技术任务也能理解主流程。
- 所有旧入口都有新入口映射。
- 页面明确下一步。

## Stage 1：文章到规则闭环

实现：

```text
导入文章
→ 提取规则
→ 审核
→ 入池
```

验收：

- 用户能独立完成文章到正式规则。
- 规则来源和引用可追溯。
- 适用条件允许未知。

## Stage 2：规则到回测闭环

实现：

```text
规则
→ 自动检查数据
→ 回测
→ 分 市场状态 统计
→ 适用性画像
→ 审核结论
```

验收：

- 回测数据缺失可一键补齐。
- 输出全周期和分市场状态结果。
- 不存在未来数据泄漏。
- 数据和版本可复现。

## Stage 3：规则到策略闭环

实现：

```text
可用规则
→ 规则比较
→ 策略草稿
→ 画像和风险配置
→ 验证
→ 发布策略版本
```

验收：

- 策略版本可回滚。
- 不每天生成正式策略。
- 规则、画像和风险配置均有版本。

## Stage 4：每日盘前闭环

实现：

```text
数据检查
→ 盘前 Kaipan
→ 市场状态
→ Daily Rule Selection
→ Daily Strategy Instance
→ Trading Day Plan
```

验收：

- 用户只需查看和批准。
- 前置数据缺失能直接修复。
- 每日结果关联正式策略版本。

## Stage 5：每日盘后闭环

实现：

```text
OHLCV 和盘后 Kaipan
→ 对比预测与实际
→ 信号归因
→ 更新适用性统计
→ 优化建议
```

验收：

- 每个信号都有明确归因。
- 规则和画像不被自动覆盖。
- 建议可接受、拒绝或观察。

## Stage 6：自动化和运维

实现：

- 定时抓取。
- 调度管理。
- 数据健康检查。
- 失败告警。
- 自动补抓。
- 成本监控。
- LLM 缓存和增量处理。
- 夜间批量回测。

# 24. 不建议采用的方式

禁止继续以下模式：

```text
新增能力
→ 新增 Sidebar 入口
→ 新增独立表单
→ 暴露大量参数
→ 执行后跳转 Job
→ 用户自己找产物
```

禁止：

- 每日生成正式策略版本。
- 直接用 LLM 推测适用市场作为生产约束。
- 回测时调用实时 Provider。
- 缺失 Kaipan 数据时默认为 false 或通过。
- 同时维护两套正式策略 Schema。
- 将文件路径作为业务引用。
- 页面直接依赖 Job 参数定义业务体验。

# 25. 最终产品状态

重构完成后，用户应感知到的产品流程是：

```text
首次：
文章
→ 规则
→ 回测
→ 策略发布

每天：
盘前计划
→ 盘后复盘

周期性：
优化建议
→ 策略草稿
→ 验证
→ 新版本发布
```

管理员感知到的系统流程是：

```text
数据源
→ 调度
→ 数据完整性
→ 任务和日志
→ 告警
→ 备份恢复
```

最核心的产品原则：

> 正式策略保持稳定，每日根据市场状态自动选择规则并生成运行实例；OHLCV 是回测底座，Kaipan 是盘前盘后和短线市场上下文；所有规则、数据、画像、策略和每日结果均版本化、可审核、可复现。


# 26. 执行保障补充

## 26.1 回归样本集不是用户前置输入

用户无需在重构开始前手工提供黄金样本集。

在 Prompt 和规则审核阶段，由系统从现有文章中自动筛选 10～15 篇候选样本，覆盖明确规则、概念、混合、模糊、市场状态、Kaipan 依赖、重复和冲突等情况。

用户只需快速确认候选样本。

在固定样本完成 Prompt、自动审核和人工审核基线前，不得批量重跑全部 100+ 篇文章。

## 26.2 阶段出口条件

每个阶段必须交付真实用户路径、测试结果、迁移验证和实施记录，才能进入下一阶段。

## 26.3 可观测性

所有业务运行需要统一运行 ID，并记录步骤状态、错误、重试、数据来源、Prompt 版本和成本。

## 26.4 数据时间语义

盘前和历史回测必须使用当时已经可获得的数据。所有快照应记录 `available_at`、`captured_at` 和 `effective_at`，防止未来数据泄漏。

## 26.5 成本控制

通过文章哈希、Prompt 缓存、规则族回测复用、增量画像和批量限流控制 LLM 与回测成本。

## 26.6 灰度迁移

新旧链路应先对照验证，再逐步切换默认入口，最后退役旧入口。任何数据和 Prompt 迁移必须支持恢复。
